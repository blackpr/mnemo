## Pitfalls learned

- Tests TRUNCATE; they must only ever use `TEST_DATABASE_URL` (`mem_test`). This bit us once.
- The server keeps the embedder and the engine it booted with. After changing `EMBEDDER`, run `admin reindex --bank <id>` and restart. After changing `ENGINE`, `reindex` moves each bank (purging the previous engine's copy; it needs the previous engine's URL and key still in the shell) and refuses to finish while a server on the old engine keeps writing: restart the server with the new `ENGINE` right after. `erase-bank` and the REST erasure refuse a bank recorded in an engine the process does not purge (`engine_mismatch`). A different width also needs `admin pin-dimensions --yes` first (it deletes every row of the previous embedder, so every bank is reindexed); setting `EMBEDDING_DIMENSIONS` explicitly changes the embedder id (`@native` becomes `@1536`), which is itself an embedder switch. The dev DB is pinned to 1536 for `openai/text-embedding-3-small@native`.
- The pin suite retypes the shared test column; `setupTestDb` resets it on every suite's setup, so do not remove that reset (the other suites mix 64- and 256-dimension rows). pgvector's HNSW caps at 2000 dimensions (`assertPinnableDimensions`).
- Session GUCs go in the pool's `options` startup parameter, not a `pool.on("connect")` query: the latter races the first statement and trips pg's deprecation.
- `npm test` with keys in `.env` would spend money; paid tests are gated behind `RUN_LIVE_TESTS=1`.
- The nested `claude -p` CLI on this machine has an expired OAuth session; use the MCP SDK client or the interactive app to exercise tools.
- `preview_start` in the desktop app looked for `launch.json` in the old scratch folder; the server is run with `npm start` in the background instead. The server does not reload code: after changing attachment code, kill the `npm start` process and start it again.
- gray-matter's default engine table evals `---js` frontmatter; the Claude Code reader passes an options object that replaces the javascript/coffee engines with throwing parsers. Keep it that way for any future Markdown importer.
- Postgres jsonb does not preserve key order; exports rebuild nested objects key by key so output is byte-stable.
- `DuplicateEpisodeError` carries the attempted (new) id, not the existing episode's id; importers can only report the externalRef of a skipped document.
- zsh expands `=word` on the command line; do not use `====` as an echo separator in shell commands.
- `governance.erasure_requests` was created in migration 0001; 0004 only adds columns and the in-flight index. The receipt digest is over canonical JSON (sorted keys) for the same jsonb key-order reason as the audit hash; `verifyReceipt` recomputes it.
- Erasure runs in the server's `ErasureWorker`: `admin erase-bank` without a running `npm start` queues the request and waits (Ctrl-C leaves it queued; `--no-wait` returns the id). A store adapter must return the same store names from `count` and `purge`; a name that appears in the inventory but not in the re-count fails the request closed, and a resumed pass decides from the counted names whether a store was already purged. The erasure tests backdate `claimed_at` by SQL to simulate a dead pass; `claimed_at` and `updated_at` are on the Postgres clock, so never compare them with `Date.now()` in a test. Never edit an applied migration file (the migrator records names): the engine-name CHECK had to become memory/0005 because 0004 had already run on both databases.
- Eval cleanup (2026-10-28): the four `eval-locomo4x-v3` banks of the extract-v3 rerun are erased tombstones (receipts verified with `verify-receipt`); erasing them revoked `eval-runner`'s key again (label `extraction-v3-2026-10-24`), so `MEM_API_KEY` in `.env` is dead and the next eval run needs another `issue-key`. bank-demo untouched (30 facts).
- The desktop app's shell may start on Node 20 (nvm default), where the npm scripts fail with `node: bad option: --env-file-if-exists`; put Node 22 first on PATH (`export PATH=$HOME/.nvm/versions/node/v22.17.0/bin:$PATH`).
- Eval cleanup (2026-10-24): the four `eval-*` banks are erased tombstones in the dev DB (receipted; `verify-receipt` passes), their Hindsight banks and Honcho workspaces are deleted (both engines hold nothing now; Honcho needs the sessions deleted before the workspace), `bank-erase-check` was erased again so its leftover grant and key went, and `bank-demo` is untouched (30 facts, 41 index rows). `eval-runner` and `eraser-check` have no live key any more (`MEM_API_KEY` in `.env` is dead; issue a new key before another eval run).
- Any new store that holds Subject data (an engine adapter, a cache) must be added to the `erasure.stores` list in `src/attachment/rest/main.ts`, `src/cli/admin.ts` and `test/helpers/erasure.ts`, or erasure cannot prove it empty. The list also carries `PgAccessRevocation`, last (so a data-store failure leaves the requester able to retry): after an erasure no key reaches the bank over REST (every grant is gone), so the final record is read with `admin erasure-status` / `verify-receipt` (the POST only returns the queued record); a principal whose only grants were on the erased bank has its keys revoked, the requester included.
- Promptfoo's built-in Anthropic provider sends `temperature: 0` unless `thinking` is configured; the API rejects `temperature` for claude-opus-5-5 (400). Both eval configs set `thinking: { type: adaptive }` on the grader provider for that reason.
- Promptfoo's `not-llm-rubric` does not invert model-graded assertions (the handler ignores `inverse`); the grader sanity cases carry `metadata.expectGraderPass` and `eval/grader/check-sanity.ts` compares verdicts.
- The Claude desktop app's auto-mode classifier refuses shell commands that print transcript text from `~/.claude/projects` or write scripts mentioning it via heredoc; the corpus builder prints statistics only and the eval files were written with the editor tools.
- Claude Code writes a resumed or forked session as a new JSONL that repeats the earlier messages; two corpus conversations (3a6c5eae, b4dc1b1e) overlap, so some drafted questions are near-duplicates. Dedupe by message uuid is still open.
- **Honcho 3.4.1 cannot drive Claude 5 models**: its Anthropic backend prefills an assistant `{` (Claude 5 rejects prefill), a thinking budget then sends `thinking.type=enabled` (also rejected), and `provider_params.extra_body` cannot replace that typed argument; its model check exempts only `claude-*-4*` names. The deriver reports the failed work units as completed. Arm D extracts with `claude-sonnet-4-5` (docker-compose.yml) while B and C use Opus 5.5: an uneven comparison on the write side.
- **Hindsight's bank delete leaves its LLM trace**: `llm_requests` rows with the full extraction prompts (the subject's text) survive `DELETE /banks/{id}` until the trace retention expires (default 1 day; checked in its embedded Postgres with psql). The adapter's `purgeBank` cannot see them; disable the trace (`HINDSIGHT_API_LLM_TRACE_ENABLED=false`) wherever an erasure receipt must mean everything.
- Honcho with `CACHE_ENABLED=false` keeps an in-process cache (cashews `mem://`, 300 s TTL) that the deriver's deletions never invalidate: get-or-create returns a deleted workspace, the next peer insert fails its foreign key as a 409, and the name is unusable for five minutes. The compose runs Redis with the cache on. Honcho deletes asynchronously (202 + deriver job) and the idle deriver backs its poll off to 30 s; the compose sets 2 s.
- Hindsight's `verbatim` extraction mode still makes one LLM call per retain (prompt-cached); re-retaining identical text under the same `document_id` is skipped by content hash even with `update_mode: replace`; recall has no result-count limit (token budget) and no as-of filter.
- Honcho embeds new messages in a background task; a search right after a write can miss it. The SDK client bound to a workspace get-or-creates it on most calls (`peer`, `session`, `sessions`, `search`), not on `workspaces()` / `deleteWorkspace()`.
- promptfoo records a provider failure (e.g. an exhausted API account) as a row with `error`; `eval:summary` and `eval:ci` exclude such rows as "not run" instead of scoring them wrong.
- The Anthropic account's credit balance ran out during the stage 2 run; the arms fail closed and the run resumes from caches and ingestion records.
- Replacing the Hindsight container (new worker id) orphans an in-flight consolidation operation; `pending_consolidation` then never drains and arm C waits for its timeout. Recover with `DELETE .../operations/{id}`, `POST .../consolidation/recover`, `POST .../consolidate`. Do not recreate the container during a run.
- Hindsight's write cost is far from linear in the smoke numbers: the 64-turn conversation cost 1.09M LLM tokens (consolidation batches of 5-8 memories at about 17k input each). Stage 2 ended at about 19 USD at list prices against a 15 USD target for that reason.

## Working agreements (from the user)

- Battle-tested, active libraries over hand-rolled code; check the installed API in `node_modules` before writing against it.
- Every commit gets an independent review agent first; at most 2 (exceptionally 3) rounds, then commit and list what was left.
- One repo, one package, no monorepo. Practical DDD: contexts as folders, pure domain, ports and adapters.
- Keep assistant context under about 50 to 60 percent: document (this file plus memory notes), then compact.

## Open follow-ups (low severity, from reviews)

- REST: duplicate `externalRef` 409 reports a fresh id instead of the existing episode's id; admin `grant` silently replaces capabilities; `revoke-key` needs the plaintext key.
- Extraction: config errors (bad provider, missing key) retry 8 times before dead; a zero-fact extraction leaves no idempotency marker (cost only); Google `taskType` hint unused.
- Extraction v3 (left after two review rounds): `fitContextToBudget` stops at the first context episode that does not fit, so one long recent episode drops older short ones (intended, a `continue` would keep more). The entity match and triage are language-naive heuristics (capitalized tokens; Latin-script acknowledgement list), with tests for Greek, CJK and Japanese. A tighter `EXTRACTION_CONTEXT_CHARS` (for example 8,000) is the next unmeasured cost lever: uncached input (context episodes, candidate facts, trigger) is about 72% of the remaining write cost on session-sized episodes, and context is the largest part of it. Hindsight's trace-reported cached tokens are still priced at full rate in `eval:summary` (whether its input count includes them is unverified).
- Retrieval (pinned index, left after two review rounds): `hnsw.max_scan_tuples` (default 20000) still bounds an iterative scan, so a bank that is a tiny share of a very large index can come back short of `limit`; `pin-dimensions` holds an ACCESS EXCLUSIVE lock for the retype and the index build (stop the server on a large index); `EMBEDDING_DIMENSIONS` set explicitly changes the embedder id (`@native` to `@1536`), an embedder switch that the message explains but that still surprises; the HNSW index (not `halfvec`) caps at 2000 dimensions.
- MCP: DNS-rebinding protection off (bearer key makes it moot on localhost); no `assert_fact` or erase tool by design.
- Erasure (left after two review rounds each on the job and the evidence commits): the `erasing` freeze is never lifted on failure, so a bank stays unwritable until a retry succeeds (intended; no unfreeze command); `alreadyPurged` trusts that a recorded store was not re-populated during the stale gap (verification still fails closed); a retry's receipt does not reference the failed request whose deletions it completes (evidence for one erasure can span two request rows, joined through the audit chain); `PgBankRepository.update` writes status and policy together, so an admin `set-extractor` racing an erasure can be reverted (pre-existing pattern for every bank update); the export status check is not under the bank lock the writers take (a tiny window for a ledger row to land during the freeze; verification would then fail closed and the retry cleans it up). From the leftovers commit (2026-10-28, two review rounds): a pass whose claim was released at shutdown may still be running its store call (or its database statement) when the next instance retakes the row, and two overlapping transactional purges can deadlock (40P01), which fails the request (a new request finishes it); shutdown can run up to 4 s past `SHUTDOWN_TIMEOUT_MS` (release and `pool.end()` each bounded at 2 s), so an orchestrator's kill grace period needs that margin; the `main.ts` shutdown wiring and `admin erase-bank --timeout` (exit 2, exclusive with `--no-wait`) are untested; `ErasureKeepsMoving` (a forced abandon that loses three rounds) is untested, and an abandon that misses on app-versus-database clock skew reports `ErasureStillRunning` with the `updatedAt` it read.
- Access revocation (left after two review rounds): a retry now revokes again any live key an earlier erasure of the bank revoked, even if its principal has since gained grants on other banks (intended: the receipts promise those keys stay revoked; such a principal needs a new key); a crash between the access purge commit and the request save records `deleted: 0` for the keys on the resumed pass (the evidence still names the principals, via the marker); `revocation_reason` has no CHECK and `erasure_request_id` no foreign key; `admin grant` and `issue-key` are not blocked by the bank freeze (a grant landing between purge and re-count fails the request closed; after the re-count it survives on the tombstone); a re-count failure strands the request until an operator re-grants `erase` on the still-`erasing` bank; erasures from before this change (`bank-erase-check`) left their grants and keys, which `verify-receipt` now reports as `not_in_receipt` failures.
- `verify-receipt` (left after two review rounds): the chain is unkeyed, so the before/at/after placement of a break bounds where the first inconsistency is, never proves the receipt's entry untouched (a run of entries rewritten and re-hashed together shows only where it ends; an anchored or keyed chain is the real fix); verification stops at the first break, so with `before_receipt` the receipt's own entry is not examined; migration governance/0008 builds its index inside the migrator's transaction and blocks audited writes for the build (on a large log, build it `CONCURRENTLY` by hand first and check `indisvalid`, see the migration); the REST record now shows an `erase` holder the ids of the other principals dedicated to the bank (same tenant, same bank's grantees; documented in the attachment README).
- Engine record (left after two review rounds): the outbox projector indexes into the server's engine whatever the bank records, so a server started with the wrong `ENGINE` writes an orphan copy that erasure (which purges the recorded engine) would miss; `reindex` catches the live case by re-counting the previous engine after the rebuild and refusing, and the server warns at boot about banks recorded elsewhere, but the projector itself has no guard yet (drop or dead-letter events for banks whose engine is not the server's); the move sequence in `admin reindex` is not unit-tested (lift it into a Retrieval application function and test with two engines); the migration backfill of `engine = 'pgvector'` is unexercised by tests and wrong for a deployment that only ever ran Hindsight or Honcho (one-off `UPDATE memory.banks SET engine = ...`, see the migration comment).
- Rate limits (left after two review rounds): the in-memory store's unref'd timer is never `shutdown()` (harmless); behind a reverse proxy every client shares the proxy's address bucket (TCP peer, never `X-Forwarded-For`); fixed windows allow a 2x burst across a reset; multi-instance needs a shared store (`@hono-rate-limiter/redis`, a `Store` over Postgres, or `rate-limiter-flexible`'s Postgres limiter), not built.
- Bank isolation guard (left after two review rounds): it sees only what the tests run (two cross-bank statements are untagged because no test runs them: the embedder row count in `admin reindex` and the boot warning in `main.ts`; migrations, functions and triggers are not checked); it checks which rows a statement touches, not the values it writes, so `INSERT ... SELECT` with a supplied other bank id and `bank_id = ANY($1)` over several banks pass; USING / NATURAL joins and unqualified columns in multi-table queries pin nothing (strict, qualify them); a `.only` left in a test makes the full-run allowlist check fail on unexercised entries, and path-filter detection reads vitest's internal `filenamePattern`. The Hindsight and Honcho `retractFact` changes (bank id instead of a scan over every bank) were not run against live engines (`npm run test:engines` spends provider credit). `concurrent appends never fork the chain` hit the 5 s timeout once in a full run on 2026-10-28 (20 appends serialized by an advisory lock on a pool of 4); it passed in five runs after.
- Portability: export ledger row and audit entry are two transactions (audit first, so a failure between them over-reports); symlinked memory files are skipped by the reader (`isFile()` is false); no MCP `export` tool yet (README lists it); the other import adapters (claude.ai export, Gemini Takeout, ChatGPT ZIP) are not built; id generation lives in the application layer rather than the attachment, unlike Memory.
- Eval: corpus is 4 conversations / 29k tokens from one tool (the plan wants 20-40 from two tools: add claude.ai, Gemini exports; dedupe forked sessions); the question audit is a model audit (`auditedBy: "model"`; the plan's human audit is open, and the type balance is uneven: fact 18, decision 9, temporal 5, preference 4, negative 4); arm A sees all turns for temporal questions (as-of by instruction only); arm B with no extraction (`EVAL_B_EXTRACTOR=none`) is implemented but not run; `eval-*` banks, Hindsight banks and Honcho workspaces are left behind after a run; embedding tokens are metered only where Hindsight reports them; a fixed wait after extraction drains stands in for a per-bank outbox count; the three transcript secret patterns in `eval/corpus/normalize.ts` belong in `SECRET_PATTERNS` in `write-extracted-facts.ts` too; `extraction.runs` keeps only the last attempt's usage; arm D cannot resume a half-ingested workspace (Honcho messages have no idempotency key) and its write tokens are whatever the deriver's process-wide counters say (the representation path's own LLM use is not captured); arm C's write cost prices prompt-cached tokens at full list price (an over-estimate); the store quality audit, governance probe grid, contradiction test and Honcho's dialectic path were not run.
- Engine adapters (stage 2, left after review): Hindsight point-in-time recall over-fetches a token budget and can starve on a bank with hundreds of live facts; Honcho's searchable probe matches through the keyword arm, so the index call proves visibility to search, not that the vector exists; neither purge inspects the engine's database (verified by hand this once).
