# One small OAuth server unlocks three chat apps

As of 28 October 2026, turning `mem` into a memory layer its owner uses every day takes four pieces of work: a public HTTPS hostname with an IPv4 address that Anthropic's, OpenAI's and Google's servers can reach; an OAuth 2.1 authorization server (the component that signs the owner in and issues access tokens to apps) inside the `mem` process that speaks the dialect the MCP (Model Context Protocol) specification now prefers (client ID metadata documents plus PKCE, a one-time code check, with dynamic registration as a fallback); a graphical user interface (GUI) served by the same Hono process; and a move from Docker to launchd-managed native Postgres with encrypted off-machine backups. With those in place `mem` reaches claude.ai, Claude Desktop and Claude mobile on every plan (Free is capped at one custom connector), ChatGPT on the web (full read and write is documented only for Business and Enterprise/Edu, Pro is documented as read/fetch only, and Plus is unverified because help.openai.com refused automated reads), and the Gemini app for personal accounts in the US, while consumer Microsoft Copilot has no custom MCP path at all and Microsoft 365 Copilot needs an administrator and a work licence. None of the consumer apps accepts `mem`'s current static bearer key, so OAuth is not optional; the coding command-line tools (Claude Code, Codex, Antigravity) keep working with that key unchanged. The cheapest reachable setup is a Cloudflare named tunnel on a domain costing about $10.46 a year, or Tailscale Funnel if no third party should be able to decrypt memory traffic, but every laptop-hosted option goes dark when the Mac sleeps, and a rented virtual private server (VPS) at roughly €7 to $12 a month is the only real fix. For OAuth, better-auth 1.7's MCP and CIMD plugins are the most complete in-process fit and panva's OpenID-certified `oidc-provider` the most mature; the MCP software development kit's (SDK's) own authorization-server helpers are frozen and should not be used. The GUI that respects "one repo, one package" is a Vite + React + shadcn/ui single-page app built to static files and served by Hono behind a same-origin cookie session, ideally reachable only on a private tailnet, and its main job is to show the provenance, supersession history, audit log and erasure receipts `mem` already stores, which no surveyed product shows together. Switching extraction from Opus 5.5 to Haiku 5.5 would cut the measured write run from 6.32 to about 0.16 USD and a heavy day from about 11 to 0.28 USD, but the under-a-dollar check that can be run today only catches large regressions. The retain policy that the evidence supports is strict model-initiated saving with server-side guards against the recall-to-retain feedback loop, plus a session-end batch for Claude Code whose facts wait as candidates for review.

## Three of four consumer apps take a remote MCP server, and none takes `mem`'s API key

Every consumer chat app that can reach `mem` does it the same way: the vendor's own cloud calls a remote MCP (Model Context Protocol, the open standard for connecting AI apps to tools and data) endpoint over HTTPS, and it authenticates with OAuth 2.1 (the standard "sign in and approve this app" flow that hands the app a short-lived access token) rather than with a pasted API key. That single fact sets the agenda. `mem`'s per-bank bearer keys can keep serving the coding tools that run on the laptop, but the chat apps need an authorization server, and they need to find it from the public internet.

### The spec in force prefers client metadata documents and tolerates dynamic registration

The current MCP revision is **2026-07-28**, succeeding 2025-11-25 ([MCP Versioning](https://modelcontextprotocol.io/specification/versioning); [MCP Changelog 2026-07-28](https://modelcontextprotocol.io/specification/latest/changelog)); no published date was found for when it moved from Draft to Current. Its non-auth changes suit `mem`'s stateless server: protocol sessions and `Mcp-Session-Id` are gone, the `initialize` handshake is replaced by a protocol version and client capabilities in each request's `_meta`, a `server/discover` call becomes mandatory, `subscriptions/listen` replaces the GET event stream and resource subscriptions, stream resumability is removed, tasks move to an extension, list results gain required `ttlMs`/`cacheScope` fields, and Streamable HTTP posts gain `Mcp-Method`/`Mcp-Name` headers. Roots, Sampling and Logging are newly deprecated, and the old HTTP+SSE transport (SSE is Server-Sent Events, a one-way streaming format over HTTP) is formally Deprecated. Clients and servers "MAY support multiple protocol versions simultaneously" ([MCP Versioning](https://modelcontextprotocol.io/specification/versioning)).

Authorization itself is optional in MCP, and stdio servers should take credentials from the environment ([MCP Authorization 2026-07-28](https://modelcontextprotocol.io/specification/latest/basic/authorization)), but an HTTP server that wants the consumer apps has to play the OAuth "resource server" role. It **MUST** publish Protected Resource Metadata (PRM, defined in RFC 9728; an RFC is an Internet standards document), a small JSON file that names at least one authorization server in `authorization_servers`, and it must make that file discoverable either through a `WWW-Authenticate: Bearer resource_metadata="..."` header on a 401 response or at a well-known URI, path-suffixed (`/.well-known/oauth-protected-resource/<mcp-path>`) or at the root ([Authorization Server Discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)). The authorization server **MUST** implement OAuth 2.1 and publish either RFC 8414 metadata or OIDC (OpenID Connect, the identity layer on top of OAuth) Discovery, and clients must refuse a metadata document whose `issuer` differs from the one they used to find it (same page). The spec builds on OAuth 2.1 draft-13, RFC 6750 (bearer tokens), RFC 8414, RFC 7591, RFC 8707 (resource indicators), RFC 9728, RFC 9207 (issuer identification), the CIMD draft (draft-00) and OIDC Discovery and Dynamic Registration ([MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)).

Four rules shape what `mem` must build. First, clients **MUST** use PKCE (Proof Key for Code Exchange, a one-time secret that stops a stolen authorization code from being redeemed), with `S256` where possible, and must refuse to proceed if the server's metadata lacks `code_challenge_methods_supported`; all authorization endpoints must be HTTPS, every redirect URI must be `localhost` or HTTPS, redirect URIs must match pre-registered values exactly, access tokens should be short-lived, and refresh tokens for public clients **MUST** be rotated ([Authorization Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)). Second, clients send the RFC 8707 `resource` parameter, set to the server's canonical URI (a path such as `https://mcp.example.com/server/mcp` is allowed, no trailing slash), on both authorization and token requests; servers **MUST** check that a token was issued for them as audience, return 401 for invalid or expired tokens, never accept tokens from the query string, and never pass a received token on to another service ([MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization); [Authorization Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)). Third, servers **SHOULD** put a `scope` in the 401 challenge, answer a token with too little scope with 403 `error="insufficient_scope"` so the client can "step up", account for scope hierarchies, and **SHOULD NOT** advertise `offline_access`; 401 means "authorize", 403 "insufficient scope", 400 "malformed request" ([MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)). Fourth, clients choose how to register in a fixed order: a pre-registered client, then a **Client ID Metadata Document** (CIMD: the client's ID is an HTTPS URL pointing at a JSON file that lists its name and redirect URIs, so the server needs no client database) if the server advertises `client_id_metadata_document_supported`, then **Dynamic Client Registration** (DCR, RFC 7591: the client posts its details to a registration endpoint and receives an ID) if a `registration_endpoint` exists, and finally asking the user ([Client Registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)). CIMD is a **SHOULD**; DCR is a **MAY** that "is deprecated and retained for backwards compatibility". A server that fetches CIMD documents must check that the document's `client_id` equals its URL, validate redirect URIs against it, guard against SSRF (server-side request forgery, where an attacker makes your server fetch internal addresses), and "clearly display the redirect URI hostname during authorization" (same pages).

The 2026-07-28 changelog adds four auth changes: authorization servers SHOULD return `iss` in authorization responses (RFC 9207) and clients MUST validate it when present (SEP-2468; a SEP is a spec enhancement proposal), DCR clients MUST send `application_type` (SEP-837), credentials are bound to the issuing server (SEP-2352), and DCR is deprecated in favour of CIMD (PR #2858) ([MCP Changelog](https://modelcontextprotocol.io/specification/latest/changelog)). A server that returns `iss` MUST advertise `authorization_response_iss_parameter_supported: true`, and a later revision is expected to make `iss` mandatory ([MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)). Helpfully for per-bank access, `tools/list` "MUST NOT vary per-connection" but "MAY vary by the authorization presented", for example by granted scopes ([MCP Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)).

The installed libraries lag the spec. `@modelcontextprotocol/sdk` 1.32.1 sets `LATEST_PROTOCOL_VERSION = '2025-11-25'` and does not list 2026-07-28 ([local SDK types.js](file:///Users/blackpr/code/mem/node_modules/@modelcontextprotocol/sdk/dist/esm/types.js)), and `@hono/mcp` 0.3.2's auth router advertises only `S256` and `client_secret_post`, has no CIMD flag, and points `resource_metadata` at the origin root rather than at a bank's path ([local @hono/mcp auth.mjs](file:///Users/blackpr/code/mem/node_modules/@hono/mcp/dist/auth.mjs)). Because `mem` puts `bankId` in the URL path, **each bank is a separate OAuth resource and a separate connector** in every app. The minimum `mem` must therefore add (an inference from the spec and Claude's client rules below) is a 401 with `resource_metadata` and `scope="mem:read mem:write"` on `POST /v1/banks/:bankId/mcp` before the MCP SDK runs; a PRM document per bank whose `resource` equals `https://<host>/v1/banks/<bankId>/mcp`, served at the path-suffixed well-known URL; RFC 8414 metadata advertising `code`, `authorization_code`/`refresh_token`, `S256`, and either CIMD with `"none"` client authentication or a registration endpoint; an `/authorize` page that signs the owner in, shows the redirect host and binds the `resource`; a `/token` endpoint that accepts form-encoded bodies and issues short-lived, audience-bound access tokens with rotated refresh tokens; and audience and scope checks on every MCP request.

### Claude: every plan, called from Anthropic's cloud, through a stricter client than the spec

Custom remote connectors are available on Free, Pro, Max, Team and Enterprise, in Claude, Cowork and Claude Desktop, with Free limited to one ([Getting started with custom connectors, help center, updated about early October 2026](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp)); on Team and Enterprise only an Owner (or, on Enterprise, a custom role that manages libraries) adds them, and members then connect with their own accounts ([Add a connector that isn't in the directory](https://claude.com/docs/connectors/custom/add-unlisted.md)). On Pro and Max the path is Customize > Connectors > "Add custom connector": enter the URL, choose "Sign in now", "Sign in when needed" or "No sign-in", and choose an OAuth client, either "Use Claude's published identity" (CIMD, recommended), "Register automatically" (DCR) or "Use your own OAuth client" (a client ID, with the secret left blank unless required, sometimes under "Advanced settings"). Authentication settings **cannot be changed after adding**; the connector must be removed and re-added (same page). "Request headers", which would let `mem` keep its static key, are "in beta and available to a limited set of organizations", entered once by an Owner, limited to four allowed header names sent exactly as typed, and cannot carry `Authorization` on an OAuth connection; Anthropic also says never to accept a token in the URL ([Add a connector that isn't in the directory](https://claude.com/docs/connectors/custom/add-unlisted.md); [Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)). The supported auth types are `oauth_dcr` and `oauth_cimd` by default, `oauth_anthropic_creds` for directory listings, `custom_connection` by arrangement, `static_headers` in limited beta and `none`; the machine-to-machine `client_credentials` grant "isn't supported" ([Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)). Anthropic says Claude "follows the 2025-03-26, 2025-06-18, and 2025-11-25 authorization specifications", recommends Streamable HTTP, still accepts the legacy SSE transport (a URL ending in `/sse` selects it), and lets Advanced > Transport override the choice ([Build an MCP server for Claude](https://claude.com/docs/connectors/building/index.md); [Add a connector that isn't in the directory](https://claude.com/docs/connectors/custom/add-unlisted.md)). No statement was found that the hosted apps speak protocol 2026-07-28.

Claude's OAuth client is stricter than the spec in ways that decide `mem`'s design. Sign-in starts only on a **401**; a `WWW-Authenticate` on a 200 is ignored. Only the first `authorization_servers` entry is used. Claude uses CIMD **only when the metadata advertises both `client_id_metadata_document_supported: true` and `"none"` in `token_endpoint_auth_methods_supported`**, and otherwise falls back to DCR. Discovery, registration and token calls get 10 seconds and refreshes 30 ([Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)). The PRM `resource` "must equal the URL as the user enters it in Claude, including any path component", the `resource_metadata` URL "can be any HTTPS location", and without one Claude probes `/.well-known/oauth-protected-resource/<mcp-path>` and then the root (same page); for server metadata it tries `/.well-known/oauth-authorization-server` before `/.well-known/openid-configuration` ([Troubleshoot your connector](https://claude.com/docs/connectors/building/troubleshooting.md)). Claude sends PKCE S256 on every request, takes scopes from the 401's `scope` or else from PRM `scopes_supported`, appends `offline_access` if the server lists it, and for the hosted apps requires the redirect URI to be registered as exactly `https://claude.ai/api/mcp/auth_callback`; it refreshes on a 401 and up to five minutes before expiry, expects `invalid_grant` for a dead refresh token and rotation for public clients (DCR and CIMD both register Claude as public), and requires `/token` to accept `application/x-www-form-urlencoded` while `/register` takes JSON ([Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)). It sends `resource` in canonical form (lowercase scheme and host, path, no trailing slash) and asks servers to compare the canonical value rather than bytes ([Troubleshoot your connector](https://claude.com/docs/connectors/building/troubleshooting.md)). A 403 triggers re-authentication only with `error="insufficient_scope"`, after which Claude retries the tool call; metadata is cached per URL for about five minutes; and with "Sign in when needed" a server can answer `initialize` and `tools/list` without a token and return 401 on a protected `tools/call`, which shows an inline Connect card (a 200 with `isError: true` does not) ([Lazy authentication](https://claude.com/docs/connectors/building/lazy-authentication.md)).

Reachability is the second constraint. "Connections come from Anthropic's cloud infrastructure, not your device", for "every Claude client, including claude.ai, Claude Desktop, Cowork, and the mobile apps" ([Getting started with custom connectors](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp)). Hostnames that resolve to private ranges, CGNAT (carrier-grade network address translation, `100.64/10`), loopback or link-local addresses are rejected, "Connectors are IPv4-only, so a hostname that only publishes `AAAA` records can't be reached", and dynamic DNS to a home NAT commonly fails ([Troubleshoot your connector](https://claude.com/docs/connectors/building/troubleshooting.md)). A cross-host redirect makes Claude drop the `Authorization` header, and a strict `Origin` check or a WAF (web application firewall) can block it ([Troubleshoot your connector](https://claude.com/docs/connectors/building/troubleshooting.md); [Test your connector](https://claude.com/docs/connectors/building/testing.md)). Anthropic's own advice for testing a local server is a public tunnel such as `cloudflared tunnel --url http://localhost:3000` or `ngrok http 3000`, with authentication left on ([Lazy authentication](https://claude.com/docs/connectors/building/lazy-authentication.md); [Test your connector](https://claude.com/docs/connectors/building/testing.md)). Outbound traffic, including authorization-server discovery, comes from **`160.79.104.0/21`** ([Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md); [IP addresses](https://platform.claude.com/docs/en/api/ip-addresses)). Anthropic's own "MCP tunnels", which need no inbound port, are a research preview for Enterprise organizations by request ([MCP tunnels](https://claude.com/docs/connectors/mcp-tunnels/overview.md)).

Once added on the web or in Desktop, a connector "is available in your conversations on the web, desktop, and mobile"; the web also renders MCP Apps, Desktop adds local extensions, and Claude Code picks up claude.ai connectors when signed in with a Claude account ([Get started with connectors](https://claude.com/docs/connectors)). Mobile cannot add one ([MCP Apps design guidelines](https://claude.com/docs/connectors/building/mcp-apps/design-guidelines)), the same authentication infrastructure backs every surface ([Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)), and `clientInfo` names such as `claude-ai` or `claude-code` are "unauthenticated" and must not be used for access decisions ([Test your connector](https://claude.com/docs/connectors/building/testing.md)).

Write tools work. Each conversation enables a connector through "+ > Connectors"; Claude asks "Allow once" or "Always allow", and per-tool settings are "Always allow", "Needs approval" or "Blocked" ([Get started with connectors](https://claude.com/docs/connectors)); the help center warns, in a fetch summary's paraphrase, that Research mode can call connector tools without further approval and that write tools should be disabled first ([Getting started with custom connectors](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp)). Tool annotations drive permissions: directory listings need a `title` plus `readOnlyHint: true` or `destructiveHint: true`, and "Read-only tools can run without per-call confirmation, and destructive tools always prompt" ([Connector pre-submission checklist](https://claude.com/docs/connectors/building/review-criteria.md); [Model Context Protocol, claude.com docs](https://claude.com/docs/connectors/building/mcp)). The same checklist asks for separate read and write tools, names of at most 64 characters, no injection-style descriptions, actionable errors, and no querying of Claude's own memory or chat history, though custom connectors are not reviewed. In the spec, `readOnlyHint` defaults to false, `destructiveHint` defaults to **true** (meaning "may perform destructive updates"), `idempotentHint` to false, and `openWorldHint` to true, with the spec itself noting that a memory tool's world is closed ([MCP schema 2026-07-28](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2026-07-28/schema.ts)); clients "MUST consider tool annotations to be untrusted unless they come from trusted servers" ([MCP Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). The server `instructions` field is guidance clients may put in a system prompt (schema, same link), and **no Anthropic page documents that the hosted apps use it**. The hosted apps support tools, prompts and resources with text and image results, but not resource subscriptions, sampling or "advanced or draft capabilities", and cap results at about 150,000 characters and calls at 240 seconds ([Build an MCP server for Claude](https://claude.com/docs/connectors/building/index.md)); failures show as "Unexpected error while invoking tool" ([Troubleshoot your connector](https://claude.com/docs/connectors/building/troubleshooting.md)); MCP Apps render on mobile in a WebView without camera, microphone or location ([MCP Apps design guidelines](https://claude.com/docs/connectors/building/mcp-apps/design-guidelines)); organization admins can mark tools `ask` or `blocked` across chat and Desktop ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)); and Anthropic warns that "malicious MCP servers may include hidden instructions" ([Getting started with custom connectors](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp)). Because `destructiveHint` defaults to true, `mem` should set it explicitly: `recall` and `list_facts` as `readOnlyHint: true`, `openWorldHint: false`; `retain`, `confirm_fact` and `dispute_fact` as `readOnlyHint: false`, `destructiveHint: false`, `openWorldHint: false` (with `idempotentHint: true` on the two status tools if they are idempotent). Whether a non-destructive write still prompts by default, and whether "always prompt" overrides a user's "Always allow", is undocumented. The "when to recall or retain" policy belongs in the tool descriptions, since `instructions` may be ignored, and `mem`'s asynchronous extraction already keeps calls far below 240 seconds.

Claude Desktop also runs local servers, but only for itself. Settings > Developer > "Edit Config" opens `~/Library/Application Support/Claude/claude_desktop_config.json`, which takes `command`/`args`/`env` stdio entries, needs a full restart, and logs to `~/Library/Logs/Claude/` ([Connect to local MCP servers](https://modelcontextprotocol.io/docs/develop/connect-local-servers)); these "aren't available in Cowork or claude.ai" (fetch-summary paraphrase of [Getting started with custom connectors](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp)). Desktop Extensions (`.mcpb`) are zip files with a `manifest.json` whose server runs locally over stdio with Desktop's bundled Node.js, auto-generated settings from `user_config`, and install by double-click; the directory no longer accepts MCPB submissions ([Build a desktop extension with MCPB](https://claude.com/docs/connectors/building/mcpb.md)); secrets go to the macOS Keychain ([Getting started with local MCP servers on Claude Desktop, help center, updated this week](https://support.claude.com/en/articles/10949351-getting-started-with-local-mcp-servers-on-claude-desktop)); and local connectors exist only in the desktop app ([Get started with connectors](https://claude.com/docs/connectors)). The sources disagree mildly on platforms: the MCPB page names macOS and Windows, the MCP site adds Linux. A tiny stdio shim forwarding to `http://localhost:8787` with the existing key would therefore work in Desktop (inferred from "can reach ... systems behind the user's firewall") but would do nothing for the phone.

Claude Code is the one Anthropic surface that connects from the user's own machine, so it reaches `localhost` directly ([Lazy authentication](https://claude.com/docs/connectors/building/lazy-authentication.md)). `claude mcp add --transport http <name> <url> --header "Authorization: Bearer ..."` keeps working; `streamable-http` is an alias for `http`, SSE is deprecated and v2.1.265+ tries HTTP first; and credential variables such as `ANTHROPIC_API_KEY` read as empty in remote URLs and headers so a project's `.mcp.json` cannot exfiltrate them ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)). It also does full OAuth: a 401 or 403 flags a server, `/mcp` or `claude mcp login` runs the browser flow, tokens are stored and refreshed, and `logout` clears them without revoking at the server; DCR and CIMD are discovered automatically, and "Incompatible auth server: does not support dynamic client registration" means a pre-configured client is needed via `--client-id`, `--client-secret` (masked, or `MCP_CLIENT_SECRET`) and `--callback-port`, which fixes the redirect to `http://localhost:PORT/callback` (v2.1.229 briefly used `127.0.0.1` and broke exact-match servers; v2.1.231 restored `localhost`); `.mcp.json` accepts `oauth.authServerMetadataUrl` and `oauth.scopes`; and `headersHelper` runs a command that prints headers, within ten seconds, re-run on 401/403, and bypassing OAuth if it returns `Authorization` (same page). Claude Code uses its own CIMD at `https://claude.ai/oauth/claude-code-client-metadata`, declaring `http://localhost/callback` and `http://127.0.0.1/callback`, which servers should match with the port ignored per RFC 8252 ([Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)). Configuration scopes are local, project (`.mcp.json`) and user; claude.ai connectors appear automatically when signed in with a subscription, a locally added server for the same URL takes precedence, and `disableClaudeAiConnectors` or `ENABLE_CLAUDEAI_MCP_SERVERS=false` opts out. Output warns at 10,000 tokens and stops at 25,000 by default (`MAX_MCP_OUTPUT_TOKENS`, or up to 500,000 characters via `_meta["anthropic/maxResultSizeChars"]`); `MCP_TOOL_TIMEOUT` defaults to about 28 hours, HTTP idles out after five minutes and calls running past two minutes move to the background; tool search loads only names and server instructions at start, server instructions and upfront descriptions are cut at **4,096 characters** (tool-search descriptions at 16,384 since v2.1.296); tools whose full `mcp__<server>__<tool>` name exceeds 128 characters are dropped; `readOnlyHint` lets read calls run in parallel, `readOnlyHint` or `idempotentHint` allows one retry after a dropped connection, and `_meta["anthropic/requiresUserInteraction"]` forces a prompt every time; resources are referenced as `@server:...`, prompts become slash commands, and elicitation is declared as `{form, url}` on 2026-07-28 and user-configured HTTP connections but form-only on claude.ai-connector connections. Since v2.1.232 a "v2 runtime (MCP TypeScript SDK 2.0, protocol revision 2026-07-28)" exists, default from v2.1.274 in some configurations and governed by `MCP_SDK_GENERATION` and `MCP_PROTOCOL_NEGOTIATION=auto|legacy`; MCP tasks are in public beta from v2.1.304, and `/mcp reconnect all` arrived in v2.1.284 (all [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)). `mem`'s current static-header setup therefore keeps working, and its tool descriptions and `instructions` should stay under 4,096 characters with the key rule first. How the v2 runtime negotiates with a server pinned to 2025-11-25 was not tested.

### ChatGPT: web-only plugins, no API keys, and a plan matrix nobody could confirm

The ChatGPT findings carry a method caveat: help.openai.com returned HTTP 403, so its claims come from search-engine extracts, and OpenAI has retitled the key article several times ("Developer mode, apps and full MCP connectors in ChatGPT [beta]", "Developer mode and MCP apps in ChatGPT", "Creating custom MCP apps in ChatGPT", "Connecting custom MCP servers in ChatGPT"), so extracts may mix versions. In those extracts, full MCP including write actions is a beta for **Business and Enterprise/Edu**, "Pro users can connect MCPs with read/fetch permissions in developer mode", workspace admins enable developer mode, and MCP apps "are not available on mobile and are web only" ([OpenAI Help: Developer mode and MCP apps, help-center extract](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt); [variant slug](https://help.openai.com/en/articles/12584461-developer-mode-apps-and-full-mcp-connectors-in-chatgpt-beta)). The developer guide also scopes custom servers to "ChatGPT on the web" ([OpenAI: Add custom MCP server](https://developers.openai.com/api/docs/guides/custom-mcp-server)) and names no plans, saying only that account and workspace policies, including Lockdown, apply ([OpenAI: Connect from ChatGPT](https://developers.openai.com/apps-sdk/deploy/connect-chatgpt)). Third parties disagree about Plus: Hatchable (updated 2026-08-21, secondary) lists developer mode for Plus, Pro, Business, Enterprise and Edu but not Free ([Hatchable](https://hatchable.com/articles/how-to-add-an-mcp-server-to-chatgpt)); Tempreon (secondary) says the help center is silent on Plus while developer docs list it, and advises treating writes on Plus as untested ([Tempreon](https://tempreon.com/guides/add-mcp-server-to-chatgpt)); Peliqan (secondary) says developer mode moved to workspace plans, so Free, Plus and Pro cannot create a custom connector ([Peliqan](https://peliqan.io/blog/chatgpt-mcp/)); and a community thread reports Business owners finding developer mode locked as an Enterprise feature with writes blocked, a claim disputed in the same thread (anecdotal) ([OpenAI Community](https://community.openai.com/t/write-actions-blocked-on-custom-mcp-server-business-plan-workspace-developer-mode-unavailable-at-workspace-level/1384381)). **The current plan matrix, especially for Plus and whether Pro has gained writes, is unverified**, and the only safe plan is to test on the owner's actual subscription.

Apps were renamed "plugins" in July 2026 and the app directory merged into one shared with Codex, so menus may say either word (secondary: [Hatchable](https://hatchable.com/articles/how-to-add-an-mcp-server-to-chatgpt); [Wikipedia: ChatGPT](https://en.wikipedia.org/wiki/ChatGPT)); the official flow is ChatGPT Plugins (chatgpt.com/plugins) → "+" → "Add custom MCP server" → URL and auth → accept the risk warning → "Create as a plugin" → install ([OpenAI: Building MCP servers](https://developers.openai.com/api/docs/mcp); [OpenAI: Connect from ChatGPT](https://developers.openai.com/apps-sdk/deploy/connect-chatgpt)). The ChatGPT desktop app shares one local MCP configuration with the Codex CLI and IDE extension, which ChatGPT on the web does not read ([OpenAI Codex docs: MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)); whether web-added plugins appear in the desktop and mobile apps after the July change is unconfirmed. Supported connections are "Server-Sent Events (SSE) and streaming HTTP" plus a Secure MCP Tunnel ([OpenAI: Add custom MCP server](https://developers.openai.com/api/docs/guides/custom-mcp-server)), remote HTTPS only (secondary: [Hatchable](https://hatchable.com/articles/how-to-add-an-mcp-server-to-chatgpt)), and calls come from OpenAI's infrastructure, optionally checked against published egress ranges and an OpenAI-managed mTLS certificate (mutual TLS: TLS is the encryption layer under HTTPS, and in the mutual form the client also presents a certificate) whose subject alternative name is `mtls.prod.connectors.openai.com` ([OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)).

ChatGPT's OAuth requirements overlap Claude's but are not identical. It uses authorization code with PKCE `S256`; it prefers CIMD, with client IDs `https://chatgpt.com/oauth/client.json` or `https://chatgpt.com/oauth/{callback_id}/client.json` and client authentication `none` or `private_key_jwt` (its keys at `/oauth/jwks.json`), falls back to DCR (registered once per server connection), or accepts predefined clients using `none`, `client_secret_post` or `client_secret_basic`; and it does **not** support client-credentials, service-account or JWT-bearer grants, **custom API keys**, or customer mTLS certificates ([OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)). The order of preference is static credentials if given, then CIMD if supported and chosen, then DCR, and mixed mode lets each tool's `securitySchemes` say `noauth` or `oauth2` ([OpenAI: Add custom MCP server](https://developers.openai.com/api/docs/guides/custom-mcp-server)). The redirect URI is the stable `https://chatgpt.com/connector_platform_oauth_redirect` **when the server supports RFC 9207 `iss`**, otherwise `https://chatgpt.com/connector/oauth/{callback_id}`; the server must serve PRM and authorization-server metadata, should turn `resource` into the token's `aud`, must verify `iss`, `aud`, `exp`/`nbf` and scopes on every request, and can trigger tool-level sign-in with a tool error carrying `_meta["mcp/www_authenticate"]`; OpenAI strongly recommends an established identity provider, naming Auth0 and Stytch and preferring ones with CIMD ([OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)).

Writes work with friction. "Write actions require confirmation by default", approvals can be remembered per tool only **within a conversation**, and full JSON inputs and outputs are inspectable ([OpenAI: Add custom MCP server](https://developers.openai.com/api/docs/guides/custom-mcp-server)); "ChatGPT currently requires manual confirmation in any conversation before write actions", and a write can happen even through a tool marked read-only ([OpenAI: Building MCP servers](https://developers.openai.com/api/docs/mcp)). Risky actions may be blocked outright, **deep research uses custom apps for read/fetch only**, and **agent mode will not use custom apps** (help-center extracts: [OpenAI Help](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt); [Connected apps in ChatGPT](https://help.openai.com/en/articles/11487775-connected-apps-in-chatgpt)). Deep research and company knowledge want read-only `search(query)` and `fetch(id)` tools returning `structuredContent` plus a JSON string, with non-empty `url`s for citations ([OpenAI: Building MCP servers](https://developers.openai.com/api/docs/mcp)); ordinary plugins need neither. MCP server **`instructions` are honoured**, with the first 512 characters kept self-contained and refreshed when the app is refreshed, and `readOnlyHint` is respected, tools without it being treated as writes ([OpenAI: Add custom MCP server](https://developers.openai.com/api/docs/guides/custom-mcp-server)); the Apps SDK reference makes `readOnlyHint`, `destructiveHint` and `openWorldHint` required, says `destructiveHint` triggers the explicit approval prompt, and stresses that hints only affect presentation ([OpenAI Apps SDK reference](https://developers.openai.com/apps-sdk/reference)). The user invokes a plugin by typing `@` and selecting it, per conversation, not automatically in every chat ([OpenAI: Add custom MCP server](https://developers.openai.com/api/docs/guides/custom-mcp-server); [OpenAI: Connect from ChatGPT](https://developers.openai.com/apps-sdk/deploy/connect-chatgpt); secondary: [Hatchable](https://hatchable.com/articles/how-to-add-an-mcp-server-to-chatgpt)). For `mem` this means OAuth with RFC 9207 `iss` (to get the stable redirect URI), all three annotations on every tool, thin `search`/`fetch` aliases over `recall` and `list_facts` if deep research should use memory, and a real test of `retain` on the owner's plan.

### The coding command-line tools already work with today's key

Codex CLI, Gemini CLI and its successor connect from the laptop and accept static headers, so they are the most reliable bridges while OAuth is built. Codex reads `[mcp_servers.<name>]` from `~/.codex/config.toml` with `url`, `bearer_token_env_var`, `http_headers`, `env_http_headers`, `http_headers_helper` and `auth = "oauth"` or `"chatgpt"`, connects unauthenticated if no credential resolves, and speaks stdio and Streamable HTTP; its OAuth (`codex mcp login`) does CIMD or DCR or a pre-registered client, with callback `http://127.0.0.1/callback` (plus a server ID without RFC 9207 `iss`) and CIMD URLs under `https://chatgpt.com/oauth/codex/`; and `default_tools_approval_mode = "writes"` prompts only for tools not marked read-only ([OpenAI Codex docs: MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)). Gemini CLI **stopped serving Google AI Pro, Ultra and free individual accounts on 2026-06-18**, per a 2026-05-19 announcement, remaining for paid API keys and Code Assist Standard/Enterprise ([GitHub discussion #27274](https://github.com/google-gemini/gemini-cli/discussions/27274); secondary: [The Register, 2026-05-20](https://www.theregister.com/ai-ml/2026/05/20/bye-bye-gemini-cli-google-nudges-devs-toward-antigravity/5243605)); its config uses `httpUrl` or `url` plus `headers`, discovers OAuth on 401 with DCR, and redirects to `http://localhost:<random-port>/oauth/callback` ([Gemini CLI docs: MCP servers](https://github.com/google-gemini/gemini-cli/blob/main/docs/tools/mcp-server.md)). Its successor, Antigravity CLI, reads `~/.gemini/config/mcp_config.json` (or `.agents/mcp_config.json`), takes `serverUrl` plus `headers`, speaks Streamable HTTP only, does DCR or a manual client with redirect `https://antigravity.google/oauth-callback`, and asks before every unconfigured tool call ([Antigravity docs: MCP](https://antigravity.google/docs/mcp/)); a v1.0.0 bug report about the OAuth token missing on `initialize`, about five months old, may be fixed (secondary: [GitHub issue #25](https://github.com/google-antigravity/antigravity-cli/issues/25)). The loopback redirects with arbitrary ports from Gemini CLI and Codex are why any DCR `mem` offers must accept loopback URIs with any port.

## A stable public hostname costs about $11 a year, but the laptop caps availability

Every hosted assistant calls `mem` from its vendor's cloud, so `localhost:8787` has to appear on the public internet as an HTTPS hostname with an IPv4 address. Claude's help center says remote servers must be reachable from Anthropic's IP ranges and that VPN or private-network servers will not connect, while confirming the auth options and the one-connector Free limit ([Claude Help: custom connectors, "Updated over 3 weeks ago" on 2026-10-28](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)); OpenAI requires a public HTTPS endpoint or its Secure MCP Tunnel, with Streamable HTTP typically at `/mcp` ([OpenAI Apps SDK: Connect from ChatGPT](https://developers.openai.com/apps-sdk/deploy/connect-chatgpt)). Every tunnel below satisfies the vendors' servers; the real differences are whether the URL survives a restart, whether streaming responses pass, who can decrypt the traffic, and whether the endpoint survives the Mac going to sleep.

Cloudflare's quick tunnels need no account or domain, give a random `trycloudflare.com` URL that changes every run and dies with `cloudflared`, are meant only for testing, cap in-flight requests at 200 (then HTTP 429), **do not support Server-Sent Events**, and offer an email-PIN gate that non-interactive clients cannot pass (page updated 2026-09-30: [Cloudflare Quick Tunnels](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/do-more-with-tunnels/trycloudflare/)); MCP's Streamable HTTP can answer with an SSE stream, so quick tunnels are out. A named tunnel needs a domain on Cloudflare (search summary of [Cloudflare Tunnel setup](https://developers.cloudflare.com/tunnel/setup)); one tunnel can publish many hostnames, each mapped to a local service with an ingress rule and an `http_status:404` catch-all, and Cloudflare applies caching, WAF and DDoS (distributed denial-of-service) protection before forwarding, which implies it terminates TLS and can see plaintext (updated 2026-10-16: [Cloudflare Tunnel routing](https://developers.cloudflare.com/tunnel/routing)). A domain's registrar need not be Cloudflare as long as its DNS is (secondary: [flaviocopes Cloudflare Tunnel guide](https://flaviocopes.com/cloudflare-tunnel/)); a .com at Cloudflare Registrar costs $10.46 for registration and renewal (aggregator, updated 2026-05-20: [domainoffer.net](https://domainoffer.net/tld/com/cloudflare)), reportedly rising about $0.71 on 2026-11-01 (aggregator, updated 2026-10-20, unverified on Cloudflare's site: [CostGoat domain comparison](https://costgoat.com/compare/domains)). Whether a CNAME-only "partial" setup works on the free plan, and whether path-based ingress within one hostname works, were not confirmed, so two hostnames is the documented route. Cloudflare Zero Trust's free plan covers up to 50 users with Access included and 24-hour log retention, with pay-as-you-go at $7 per user per month ([Cloudflare Zero Trust plans](https://www.cloudflare.com/plans/sase-zero-trust.md)). Cloudflare's proxy read timeout is **125 seconds** (HTTP 524) and its idle timeout 900 seconds, configurable only on Enterprise (updated 2026-10-22: [Cloudflare connection limits](https://developers.cloudflare.com/fundamentals/reference/connection-limits/)), which **conflicts with a third-party 100-second figure** that the official page supersedes ([http.dev 524](https://http.dev/524)); SSE passes as an uncached stream but long silences get cut, so `mem` should send keepalive pings more often than the shortest timeout in the chain (secondary: [StackHarbor SSE behind Cloudflare](https://stackharbor.com/en/knowledge-base/cffix-websockets-sse-behind-cloudflare/)). When no `cloudflared` connector is healthy, the hostname returns error 1033 (updated 2026-04-23, just over six months old: [Cloudflare error 1033](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1033/)), and `cloudflared service install` runs it as a login-time launch agent or, with `sudo`, a boot-time daemon (updated 2026-04-17, borderline possibly stale: [Cloudflare: run cloudflared as a macOS service](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/as-a-service/macos/)).

Tailscale Funnel is in Beta, available on all plans, needs Tailscale v1.38.3+, MagicDNS, HTTPS certificates and a `funnel` node attribute, and is off by default; it listens only on ports 443, 8443 and 10000, has non-configurable bandwidth limits, supports only `tailnet-name.ts.net` names, can take up to 10 minutes for new DNS to propagate, terminates TLS in the Tailscale client on the device so relays "cannot decrypt" traffic and hide the device's IP, cannot share one port with Serve, is subject to Let's Encrypt rate limits, and on macOS needs the App Store or Standalone build (last validated 2026-01-20, possibly stale: [Tailscale Funnel KB](https://tailscale.com/kb/1223/funnel)). No throughput figure is published (secondary, September 2026: [SSD Nodes on Funnel limits](https://www.ssdnodes.com/learn/tailscale-funnel-limits-and-ports); [Tailscale forum](https://forum.tailscale.com/t/bandwidth-for-free-users/5242)), which matters little for one user's text traffic but is unverified. Tailscale Serve, by contrast, is tailnet-only, provisions TLS for `device.tailnet.ts.net`, adds `Tailscale-User-Login`, `-Name` and `-Profile-Pic` headers while stripping spoofed copies, and recommends that the backend listen only on localhost (also validated 2026-01-20: [Tailscale Serve KB](https://tailscale.com/kb/1312/serve)); the Personal plan is free for up to six users with unlimited devices ([Tailscale pricing](https://tailscale.com/pricing)).

ngrok's free plan includes 1 GB of data out, 20,000 HTTP requests, 10,000 log events and 3 OAuth monthly active users a month, 4,000 requests per minute, three endpoints and one dev domain that "doesn't change when you restart the agent", and no endpoint timeout; free endpoints show an **interstitial warning page in front of HTML browser traffic** (API clients are unaffected), which a "Visit" click suppresses for seven days and which only a client-sent `ngrok-skip-browser-warning` header, a non-standard User-Agent or a paid plan removes ([ngrok free plan limits](https://ngrok.com/docs/pricing-limits/free-plan-limits)). A forum user found that setting the skip header server-side does nothing because the page is served at ngrok's edge ([Laracasts thread](https://laracasts.com/discuss/channels/laravel/remove-warning-page-in-ngrok-server)). The interstitial would therefore land on `mem`'s OAuth login and GUI pages in the owner's browser about once a week; whether the "Visit" click preserves an `/authorize` query string is undocumented.

OpenAI's Secure MCP Tunnel runs a `tunnel-client` inside your network that long-polls `api.openai.com:443` (or mTLS to `mtls.api.openai.com`) for queued MCP requests, needs a Platform `tunnel_id`, an API key and Tunnels permissions, defaults to 600 requests a minute, 10 MiB per request and a **120-second deadline**, works for ChatGPT ("Connection: Tunnel"), Codex and the Responses API, and states no plan availability ([OpenAI Secure MCP Tunnels](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)); a third-party write-up dates it to May 2026 and notes the full tool-call payload passes through OpenAI's control plane, which it could not fully verify ([mer.vin write-up](https://mer.vin/2026/05/openai-secure-mcp-tunnel-private-mcp-servers-for-chatgpt-codex-and-the-api/)). It does nothing for Claude or Gemini.

### Identity in front of the server: three supported patterns

A plain Cloudflare Access application blocks the vendors, because non-browser clients receive a 302 to a login page they cannot complete; Access's **Managed OAuth** instead makes Access itself an OAuth authorization server for self-hosted apps, MCP server applications and MCP portals, answering unauthenticated non-browser clients with 401 plus discovery, offering toggleable DCR with HTTPS-only redirects, issuing opaque 15-minute tokens, and requiring clients that support RFC 8707; the origin must validate the `Cf-Access-Jwt-Assertion` header, and Cloudflare warns not to enable it in front of a server that runs its own OAuth, because it replaces the 401 behaviour; the page names neither claude.ai nor a plan (updated 2026-07-01: [Cloudflare Managed OAuth](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/managed-oauth/)). Cloudflare's guide for securing MCP servers says a self-managed server on your own hostname keeps its own OAuth with Access policies defining who may use it, needs a Zero Trust organization with One-time PIN or an identity provider, and needs the hostname proxied (updated 2026-10-22: [Cloudflare: Secure MCP servers](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/secure-mcp-servers/)). **MCP server portals** front up to 80 upstream servers at one `https://<subdomain>.<domain>/mcp`, authenticate clients with managed OAuth or service tokens, reach upstreams with DCR, manual OAuth credentials, **a bearer token** or custom headers, need an active Cloudflare domain and an identity provider, and name Claude Desktop, Workers AI Playground, OpenCode, Windsurf and MCP Inspector as clients but not ChatGPT (updated 2026-10-27: [Cloudflare MCP server portals](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/)); an older changelog first announced OAuth for MCP in Access (2025-08-26, possibly stale and superseded: [Cloudflare changelog](https://developers.cloudflare.com/changelog/post/2025-08-26-access-mcp-oauth/)). Access policies are Allow, Block, Bypass and Service Auth; Bypass "does not enforce any Access security controls and requests are not logged", and Cloudflare suggests Service Auth instead for permanent access (updated 2026-10-01: [Cloudflare Access policies](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/)); and with "Require Access protection" switched on, hostnames without an Access app are blocked by default ([Cloudflare: Require Access protection](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/require-access-protection)). Cloudflare's `workers-oauth-provider` library covers PKCE, DCR, RFC 8414/9728, CIMD, RFC 8707 and the MCP spec with hashed tokens in Workers KV (Cloudflare's key-value store), but runs on Workers and does not proxy to an external origin ([cloudflare/workers-oauth-provider](https://github.com/cloudflare/workers-oauth-provider)). ngrok's `oauth` traffic-policy action is a cookie-and-redirect browser flow that would block vendor servers unless scoped away from `/mcp`; the page shows `expressions` on rules but no path exclusions ([ngrok OAuth action](https://ngrok.com/docs/traffic-policy/actions/oauth/)). Funnel has no identity layer at all; its "identity in front" is Serve.

That leaves three patterns. Pattern C, which fits if `mem` builds its own OAuth, puts two hostnames on one tunnel: `mcp.<domain>` with no Access app (or a path-scoped Bypass for `/mcp`, `/.well-known/*` and the OAuth endpoints), protected by `mem`'s own OAuth, and `gui.<domain>` behind an Access Allow policy with a One-time PIN or GitHub/Google login. Pattern A (Managed OAuth) or B (a portal that calls `mem` with its existing bearer key) would let `mem` skip building OAuth, at the cost of a Zero Trust organization and identity provider, identity tied to Cloudflare, and an untested dependency on claude.ai's and ChatGPT's clients interoperating with Access's opaque tokens, DCR and RFC 8707 handling; no Cloudflare, Anthropic or OpenAI page confirms that the hosted apps complete those flows, Access's page mentions only DCR and not CIMD, and portal and Managed OAuth pricing is unstated beyond Enterprise-only log push. On Funnel, the equivalent split is Funnel on port 443 for MCP and Serve on 8443 or 10000 for a tailnet-only GUI.

### IP allowlists harden two endpoints at most

Anthropic publishes one stable outbound block, `160.79.104.0/21`, used "when making MCP tool calls to external servers", plus inbound `160.79.104.0/23` and IPv6 `2607:6bc0::/48`, lists five phased-out `34.162.x.x` addresses to remove, and says the addresses "will not change without notice" ([Anthropic IP addresses](https://platform.claude.com/docs/en/api/ip-addresses)); the help center says private-network servers must allowlist them ([Claude Help: custom connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)), and a third party describes `160.79.104.0/21` as Anthropic's only published outbound range, IPv4 only ([Zuplo on Anthropic-managed agents](https://zuplo.com/learn/mcp/authentication/anthropic-managed-agents)). OpenAI publishes machine-readable `https://openai.com/chatgpt-connectors.json` (plugins, connectors, GPT Actions) and `chatgpt-agents.json` (Codex cloud), each with a `creationTime` and `prefixes`, warns that ranges change and should be fetched automatically, says an allowlist identifies networks rather than users and is no substitute for auth, and recommends mTLS plus OAuth 2.1 ([OpenAI IP egress ranges](https://developers.openai.com/api/docs/guides/ip-addresses)); forum users report calls from unlisted addresses, an OpenAI representative calls the list "best effort", and another reply attributes Azure-range traffic in developer mode to Microsoft infrastructure (forum posts, not docs: [OpenAI community: unlisted IPs](https://community.openai.com/t/whitelisted-openai-ips-from-chatgpt-connectors-json-but-seeing-calls-from-other-ips-when-i-call-my-app/1372382); [OpenAI community: stability of ranges](https://community.openai.com/t/how-stable-is-chatgpt-s-published-egress-ip-ranges-for-apps/1368080)). An allowlist can therefore only harden the server-to-server paths, `/mcp` and perhaps `/token`, never `/authorize`, the login page, `/.well-known/*` or the GUI, which the owner's browser loads from anywhere; it needs a sync job for OpenAI's list; it would also block the owner's own direct clients unless exempted; and Funnel cannot enforce one at its edge, while whether Funnel or ngrok forward the original client IP was not checked.

### What a laptop can and cannot promise

Sleep stops Node, Postgres, `cloudflared` and `tailscaled` alike. On a MacBook, System Settings → Battery → Options → "Prevent automatic sleeping on power adapter when the display is off" keeps a plugged-in Mac awake, and "Wake for network access" wakes it briefly for local shared services, not for inbound tunnel traffic (undated page for macOS 27: [Apple: Set sleep and wake settings](https://support.apple.com/guide/mac-help/prevent-your-mac-from-sleeping-mchle41a6ccd/mac)); Apple warns that preventing sleep costs power and varies by model (search summary of the same page). `caffeinate` with no flags prevents idle sleep, `-s` prevents system sleep but "is valid only when system is running on AC power", `-i` prevents idle sleep and `-w <pid>` holds until a process exits (old man page, behaviour stable: [caffeinate(8) mirror](https://www.unix.com/man-page/osx/8/CAFFEINATE); [ss64 mirror](https://www.uucp.hu/mirror/ss64.com/osx/caffeinate.html)). A third-party blog says closing the lid on battery forces sleep that no software assertion can override, unconfirmed by Apple ([OpenReplay blog on caffeinate](https://blog.openreplay.com/mac-awake-overnight-agent-runs-caffeinate/)), and closed-display (clamshell) mode needs power, an external display and an external keyboard and mouse, per an Apple-hosted community copy and a vendor guide rather than Apple's own article ([Apple Community thread](https://discussions-jp-prz.apple.com/thread/252123651); [OWC guide](https://eshop.macsales.com/blog/64640-how-to-use-your-mac-laptop-in-closed-display-clamshell-mode/)). ngrok advises running its agent as a background service ([ngrok free plan limits](https://ngrok.com/docs/pricing-limits/free-plan-limits)). The honest promise for laptop hosting is "reachable while the Mac is open or docked on power": outbound tunnels reconnect after network changes but captive portals block them, Power Nap does nothing for inbound sessions, and a claude.ai conversation using `mem` will see 1033 errors or timeouts while the lid is closed. How `cloudflared`, `tailscaled` and Docker behave across sleep and wake was not documented in what was read.

## Embed a mature OAuth library and own only the thin resource-server layer

An OAuth deployment has two halves. The **authorization server** signs the owner in, shows a consent page, and issues tokens; the **resource server** (here, `mem`'s MCP route) checks each token and decides what it may do. The research found that the resource-server half is small and safe for `mem` to own, while the authorization-server half should come from a battle-tested library or service.

### The MCP SDK's authorization-server helpers are frozen, and the Hono port inherits their gaps

In the installed SDK v1 (1.32.1; the latest v1 is 1.32.2, published 2026-10-23 per [npm](https://www.npmjs.com/package/@modelcontextprotocol/sdk)), `mcpAuthRouter` and `mcpAuthMetadataRouter` are Express-only (`/Users/blackpr/code/mem/node_modules/@modelcontextprotocol/sdk/dist/esm/server/auth/router.d.ts`), the `OAuthServerProvider` interface leaves client storage, code and token minting, refresh and revocation to the implementer (`/Users/blackpr/code/mem/node_modules/@modelcontextprotocol/sdk/dist/esm/server/auth/provider.d.ts`), `requireBearerAuth` is Express middleware with an optional `expectedResource` check (`/Users/blackpr/code/mem/node_modules/@modelcontextprotocol/sdk/dist/esm/server/auth/middleware/bearerAuth.d.ts`), `client_id_metadata_document_supported` appears only in client and shared code, never under `server/auth/`, so the helpers do not implement CIMD (grep of `/Users/blackpr/code/mem/node_modules/@modelcontextprotocol/sdk/dist/esm`), and the README labels its in-memory provider an "OAuth demo authorization server" without calling the router itself demo-only (`/Users/blackpr/code/mem/node_modules/@modelcontextprotocol/sdk/README.md`). SDK v2 (`@modelcontextprotocol/server` 2.4.0, 2026-10-23, and `@modelcontextprotocol/hono` 2.0.2, 2026-10-02, per [npm](https://www.npmjs.com/package/@modelcontextprotocol/server)) moves those helpers into `@modelcontextprotocol/server-legacy/auth` as a "deprecated, frozen v1 copy" and tells servers to "migrate AS to a dedicated IdP/OAuth library" (AS meaning authorization server, IdP identity provider), calling the frozen copy only "a supported interim choice" ([SDK v2 upgrade guide](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2)). What v2 keeps is the resource side: the SDK "never issues" tokens, exports a fetch-style `requireBearerAuth` (naming Hono) and `oauthMetadataResponse` for PRM, rejects tokens without `expiresAt`, and advises "Use a dedicated identity provider for new servers"; its `@modelcontextprotocol/express` 2.0.1 silently drops `expectedResource`, leaving audience unchecked ([SDK v2: Require authorization](https://ts.sdk.modelcontextprotocol.io/v2/serving/authorization.html)). An open issue, opened 2026-09-03, reports that the SDK's defaults serve PRM only at the root with the origin as `resource` for path-mounted endpoints, which stricter clients such as Gemini CLI and Antigravity reject ([typescript-sdk#2751](https://github.com/modelcontextprotocol/typescript-sdk/issues/2751)), and that is exactly `mem`'s per-bank layout.

`@hono/mcp` (installed 0.3.2, latest 0.3.5 published 2026-10-28 per [npm](https://www.npmjs.com/package/@hono/mcp)) ports the same router to Hono with `mcpAuthRouter`, `ProxyOAuthServerProvider`, authorize, token, registration and revocation handlers, `wellKnownRouter`, `simpleMcpAuthRouter` and `bearerAuth`, needing `hono-rate-limiter` for rate limits (`/Users/blackpr/code/mem/node_modules/@hono/mcp/dist/auth.d.mts`). Its authorize handler requires S256, accepts `resource`, and matches redirects exactly except for loopback ports; its metadata advertises only `client_secret_post` and no CIMD flag, so Claude would never choose CIMD against it; in 0.3.2 DCR secrets come from `Math.random()`, are compared with `!==`, and every rate limiter shares one global key; and `bearerAuth` emits a non-standard `error="Unauthorized"` with `resource_metadata` at the root, though `wellKnownRouter` does serve path-aware PRM; its transport passes `ctx.get("auth")` on to tool handlers as `authInfo` (`/Users/blackpr/code/mem/node_modules/@hono/mcp/dist/auth.mjs`; `/Users/blackpr/code/mem/node_modules/@hono/mcp/dist/index.mjs`). The 0.3.5 changelog fixes the rate-limit key and the secret generator ([@hono/mcp CHANGELOG](https://github.com/honojs/middleware/blob/main/packages/mcp/CHANGELOG.md)); the README documents only `simpleMcpAuthRouter` for third-party providers and says nothing about CIMD or SDK v2 ([@hono/mcp README](https://github.com/honojs/middleware/blob/main/packages/mcp/README.md)); and RFC 6750 defines only `invalid_request`, `invalid_token` and `insufficient_scope` as bearer error codes ([RFC 6750 §3.1](https://datatracker.ietf.org/doc/html/rfc6750#section-3.1)). Hono 4.13.13 already ships a `jwk` middleware with `jwks_uri`, `alg` and `aud` verification, and `jose` 6.2.13 is installed through the SDK (`/Users/blackpr/code/mem/node_modules/hono/dist/types/middleware/jwk/jwk.d.ts`; `/Users/blackpr/code/mem/node_modules/hono/dist/types/utils/jwt/jwt.d.ts`). Building `mem`'s authorization server on `mcpAuthRouter` would break the "battle-tested over hand-rolled" rule, lack CIMD and rest on code upstream has frozen. Neither has a public report of claude.ai or ChatGPT completing CIMD against it, so the first evening of work should be a spike that connects claude.ai, ChatGPT, Gemini and Claude Code to a throwaway bank before anything else is built.

### One user, one passkey, one honest consent page

For a single owner the login should be a passkey, with a password-plus-TOTP (time-based one-time code) or recovery-code fallback set up once from the command line and sign-up switched off afterwards. better-auth's `@better-auth/passkey` (1.7.14) requires an existing session to register by default, which `registration.requireSession: false` plus `registration.resolveUser` changes for passkey-first onboarding; its page does not cover disabling sign-up ([better-auth Passkey plugin](https://www.better-auth.com/docs/plugins/passkey); [npm @better-auth/passkey](https://www.npmjs.com/package/@better-auth/passkey)). Magic links are best avoided, since they need email sending and two of better-auth's 2026 advisories sat in those code paths ([better-auth security advisories](https://github.com/better-auth/better-auth/security/advisories)). The consent page **MUST** name the client, show the scopes and the registered `redirect_uri`, use CSRF protection and block framing, and consent cookies **MUST** use the `__Host-` prefix, `Secure`, `HttpOnly`, `SameSite=Lax`, be signed and be bound to the `client_id` ([MCP Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)); the authorization server **MUST** clearly show the redirect hostname and SHOULD warn about localhost-only redirects, which CIMD cannot protect ([MCP Security Considerations 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)); Claude's docs repeat the hostname rule ([Claude: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)); and better-auth's September advisory about device approval that "does not show the requesting client or permissions" shows that the consent screen's content is a security property ([better-auth security advisories](https://github.com/better-auth/better-auth/security/advisories)). Remembered consent exists in both libraries (`loadExistingGrant`; consent records) and `skip_consent` is admin-only ([oidc-provider docs](https://raw.githubusercontent.com/panva/node-oidc-provider/main/docs/README.md); [better-auth OAuth 2.1 Provider](https://www.better-auth.com/docs/plugins/oauth-provider)). A workable flow (an inference) is a `mem auth bootstrap` command that prints a one-time enrolment URL, a passkey plus recovery codes, permanent sign-up lockout, and a consent page that reads like "ChatGPT (chatgpt.com) wants read and write access to bank personal at https://mem.example.com/v1/banks/personal/mcp; it will redirect to chatgpt.com", never with an erase or admin checkbox and never with `skip_consent` for the chat apps. How passkeys behave inside claude.ai's in-app browser or ChatGPT's mobile pop-up is untested.

### OAuth clients become integration principals with one grant each

`mem` already has the right model: `governance.principals(id, tenant_id, kind CHECK IN ('human','agent','integration'), display_name)`, `governance.grants(principal_id, bank_id, capabilities text[], granted_at, expires_at)` and `governance.api_keys(key_hash, principal_id, label, created_at, revoked_at)`, with the REST layer resolving `deps.scopes.resolve(bearerToken(authorization), bankId)` (`/Users/blackpr/code/mem/src/governance/infrastructure/postgres/migrations/0001_governance.sql`; `/Users/blackpr/code/mem/src/attachment/rest/app.ts`). The token's audience must be the bank's canonical URI and anything else must be rejected ([MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization); [MCP Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)), and PRM's `resource` must equal the URL the user typed ([Claude: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)). RFC 9068 tokens carry `iss`, `exp`, `aud`, `sub`, `client_id`, `iat`, `jti` and `scope` ([RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html)), better-auth emits `azp` instead of `client_id` ([better-auth OAuth 2.1 Provider](https://www.better-auth.com/docs/plugins/oauth-provider)), and Zitadel's shared audience would require checking `azp` ([Zitadel DCR](https://zitadel.com/docs/guides/integrate/dynamic-client-registration)). CIMD client IDs are stable URLs, ChatGPT's `https://chatgpt.com/oauth/client.json` and Claude Code's `https://claude.ai/oauth/claude-code-client-metadata`, while Claude under DCR "register[s] a new client on every fresh connection" ([OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth); [Claude: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)). Servers must account for scope hierarchies, should step up with 403 `insufficient_scope`, and should avoid omnibus scopes ([MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization); [MCP Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)). Revocation tools differ: better-auth's `POST /oauth2/revoke` also kills the access tokens a refresh token minted but JWTs live until expiry ([better-auth OAuth 2.1 Provider](https://www.better-auth.com/docs/plugins/oauth-provider)), and `oidc-provider` revokes by token or grant ([panva/node-oidc-provider](https://github.com/panva/node-oidc-provider)). Claude's static headers represent an organization, not a person, and Claude Code can do OAuth through its CIMD and a loopback redirect ([Claude: Authentication for connectors](https://claude.com/docs/connectors/building/authentication)).

The mapping that follows (an inference, since no published best practice exists) is one **principal per connected client**, created at consent time with an id like `oauth:<sha256(iss|client_id)>`, `kind='integration'` and a display name from the CIMD `client_name` and host, recorded in a new `governance.oauth_clients(iss, client_id, principal_id, revoked_at, ...)` table that mirrors `api_keys`; the human `sub` goes into audit details as "on behalf of", so the audit log tells claude.ai, ChatGPT and Claude Code apart for free. Each principal gets a grant on exactly the bank named by the token's audience. On every MCP request `mem` verifies the JWT with `audience` set to the route's canonical bank URL, looks up the principal from `(iss, client_id or azp)`, loads the grant for `(principal, bankId)`, and intersects token scopes with grant capabilities: `mem:read` maps to `read`, `mem:write` to `write` (implying `read`), and `admin` and `erase` are never requestable, absent from `scopes_supported`, and rejected if a token claims them. A token for bank A fails at bank B before any database read. Revoking a client is immediate, because the scope is re-resolved per request: set `revoked_at` or delete the grant, then revoke its refresh tokens and consent at the authorization server, with five-to-fifteen-minute access tokens as the backstop. API keys stay as a second credential type behind the same resolver, branching on token shape (a three-part JWS (the signed form of a JWT) goes to key-set verification, anything else to the sha256 lookup), so Claude Code and scripts keep static keys and only API-key principals can hold `admin` or `erase`; an unauthenticated request must still get the 401 with `resource_metadata`. If a client falls back to DCR, principals multiply per connection, which advertising CIMD properly avoids; whether claude.ai reuses one token across several per-bank connectors was not verified.

### The pitfalls that matter for a one-person server

Open DCR is an unauthenticated write endpoint that invites client sprawl ([WorkOS blog, 2026-08-12](https://workos.com/blog/mcp-client-identity-dcr-cimd-auth-md)); the spec deprecates it ([MCP Client Registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)); better-auth keeps it behind two flags with resource allowlists ([better-auth OAuth 2.1 Provider](https://www.better-auth.com/docs/plugins/oauth-provider)); and Descope restricts it by callback pattern ([Descope](https://docs.descope.com/agentic-identity-hub/mcp-servers/registration-methods)). Redirect URIs must match exactly, with loopback ports the only exception, and proxies **MUST** use "exact string matching (not pattern matching or wildcards)" ([MCP Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations); [MCP Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices); [Claude: Authentication](https://claude.com/docs/connectors/building/authentication)), and CVE-2026-67333 shows what loose validation costs ([Corgea](https://corgea.com/advisories/vulnerabilities/CVE-2026-67333)). The confused-deputy rule (per-client consent before forwarding) matters only if `mem` fronts an upstream identity provider, for example through `ProxyOAuthServerProvider` (`/Users/blackpr/code/mem/node_modules/@hono/mcp/dist/auth.d.mts`; [MCP Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)). Audience checks and the no-passthrough rule are mandatory, and two 2026 library bugs (the Express `expectedResource` drop and better-auth accepting session JWTs) show they fail silently ([SDK v2 authorization](https://ts.sdk.modelcontextprotocol.io/v2/serving/authorization.html); [better-auth releases](https://github.com/better-auth/better-auth/releases)). Refresh tokens must rotate for public clients, Claude wants `invalid_grant` and the new refresh token in the same response, and the defaults are one hour and 30 days in better-auth and one hour and 14 days in `oidc-provider` ([MCP Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations); [Claude: Authentication](https://claude.com/docs/connectors/building/authentication); [better-auth MCP](https://www.better-auth.com/docs/plugins/mcp); [oidc-provider docs](https://raw.githubusercontent.com/panva/node-oidc-provider/main/docs/README.md); [Corgea: CVE-2026-53512](https://corgea.com/advisories/vulnerabilities/CVE-2026-53512)). CIMD fetching needs SSRF and rebinding protection that should not be hand-rolled, and allowlisting CIMD hosts is permitted ([MCP Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices); [better-auth CIMD](https://www.better-auth.com/docs/plugins/cimd); [Clerk changelog](https://clerk.com/changelog/2026-09-17-client-id-metadata-documents-ga)). Emitting `iss` prevents mix-up attacks and unlocks ChatGPT's stable redirect ([OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)); path-aware discovery is broken by default in the SDK ([typescript-sdk#2751](https://github.com/modelcontextprotocol/typescript-sdk/issues/2751)); and a WAF in front of the authorization server can break discovery from `160.79.104.0/21` ([Claude: Authentication](https://claude.com/docs/connectors/building/authentication)). The OAuth 2.1 draft and RFC 9700 were not read directly; their requirements come as the MCP spec restates them. Translated into `mem` guardrails: advertise CIMD (with `none`) and keep DCR off or restricted to `claude.ai`, `chatgpt.com` and loopback redirects (Gemini and Copilot Studio will need it on); allowlist CIMD hosts; issue JWTs of 15 minutes or less with `aud` set to the bank URL and the issuer pinned; rotate refresh tokens with lifetimes of 30 days or less; never hand the access token to the extraction provider; never expose `erase` or `admin` over OAuth; rate-limit `/authorize`, `/token` and registration per IP and client; set `frame-ancestors 'none'` on login and consent; and write every consent, issuance and revocation to the hash-chained audit log. With one possible consenter, the passkey and the consent page are the decisive controls: an attacker who registers a client still needs the owner to approve a page that shows the attacker's redirect host.
## The GUI's job is to show what `mem` already knows, from a Vite app Hono serves

No surveyed memory product shows, in one place, where a memory came from, what it replaced, which app read or wrote it, and proof that it was deleted. `mem` already stores all of that (validity intervals, recorded-at, provenance episodes, writer and extractor model, status, supersession links, a hash-chained audit log and erasure receipts), so the GUI's design problem is display and control, not new concepts.

The v1 screens follow from that evidence. A **facts table** with statement, status (asserted, confirmed, disputed), "true from–to" (or "present"), recorded-at, writer and source-episode count, filterable by status, client, bank and "include superseded" (OpenMemory's filters, Supermemory's `isLatest`). A **fact drawer** with the verbatim source quote, episode link, writer and extractor model, answering "where did this come from" from data, never by asking a model. **Confirm, dispute and correct** inline with toast-level undo, where "correct" creates a superseding fact. A per-fact **history timeline** with the two time axes labelled separately and status changes interleaved. One **"as of" date picker** with a banner and a return-to-now link. An **audit view** filtered by client, operation and fact, with a per-fact "accessed by" panel and per-client cards. **Erase with a dry-run preview** of the episodes and derived facts to be removed, explicit confirmation and a downloadable receipt. **Export** as an unlocked per-bank button (JSONL and Markdown). Later polish: a review queue for new facts ordered by evidence, a graph or 2D bitemporal view, side-by-side diffs for corrections, and per-client pause. The mistakes to avoid are a lossy prose summary as the main view, editing only through prompts, irreversible bulk resets, deletion that leaves derived data, asking the model what it used, imports that commit without review, UI and store drift, and locked export. `mem`'s hash-chained audit log has no UI precedent to borrow from, so its chain-verification display needs its own design.

|---|---|---|---|

The ranking is therefore: a **Vite react-ts SPA built into `dist/web` and served by `serveStatic`** (one package, one process, official CLI); Hono JSX with htmx (no build step, cheapest tests, but not a framework-CLI stack and mid-transition between htmx 2 and 4); Next.js static export (works, but forbids `facts/[id]`-style dynamic routes without generated params and adds about 280 MB); TanStack Start or React Router in SPA mode (frameworks whose server half goes unused); and HonoX or Astro last. The build output should be git-ignored, served by absolute path, and must not overlap any route prefix guarded by middleware.

### The GUI should log in with a same-origin cookie, ideally on a private hostname

"OAuth 2.0 for Browser-Based Applications" became **RFC 10017 / BCP 212 (a Best Current Practice) in August 2026**, ranking three patterns from most to least secure: a backend-for-frontend (BFF, where the server holds the tokens and the browser holds only a session cookie), "strongly recommended" for personal-data apps; a token-mediating backend; and a browser-held public client with PKCE, "vulnerable to all the attack scenarios" described ([IETF Datatracker: draft-ietf-oauth-browser-based-apps](https://datatracker.ietf.org/doc/draft-ietf-oauth-browser-based-apps/); [RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html)). Its section 7.1 goes further: "Too often, simple applications are made needlessly complex by using OAuth to replace the concept of session management", so a same-domain frontend and API can use server-side cookie sessions; cookies MUST be `Secure` and `HttpOnly` and SHOULD be `SameSite=Strict`, `Path=/`, without `Domain`, with a `__Host-Http-` style prefix; SameSite=Strict "falls short" when other apps share the site; a CSRF (cross-site request forgery) defence is mandatory, ideally CORS plus a custom request header; and tokens in localStorage are readable by any injected script ([RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html)). OWASP (the Open Worldwide Application Security Project) lists synchronizer tokens, signed double-submit cookies, Fetch Metadata (`Sec-Fetch-Site`), custom headers with an exact CORS allowlist, and full-origin checks that reject `null`, says SameSite "does not replace a proper CSRF defense", forbids state changes on GET, and recommends re-authentication for high-risk actions ([OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)). Hono's built-in `csrf()` checks `Origin` and `Sec-Fetch-Site` but **only for form-sendable content types**, so it skips `application/json` requests ([Hono: CSRF middleware](https://hono.dev/docs/middleware/builtin/csrf)). Tailscale Serve proxies tailnet traffic to `127.0.0.1`, adds `Tailscale-User-Login`, `-Name` and `-Profile-Pic` (plus `Tailscale-App-Capabilities` on v1.92+) only for tailnet traffic, strips incoming copies, and warns that a backend not listening only on localhost lets "any user ... supply their own header values" (last validated 2026-01-20, possibly stale: [Tailscale: Serve](https://tailscale.com/kb/1312/serve)). The MCP transport rules require servers to validate `Origin` against DNS rebinding and to bind locally to 127.0.0.1 (spec 2025-11-25, more than six months old: [MCP spec 2025-11-25: Transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)), and `mem` today authenticates REST and MCP with per-bank bearer keys and has deferred OAuth (`/Users/blackpr/code/mem/src/attachment/rest/app.ts`).

The design that follows has a strong default and a fallback. The default is a **tailnet-only GUI**: bind a second, loopback-only listener for GUI routes, front it with `tailscale serve`, accept `Tailscale-User-Login` only on that listener and only for the one configured login, keep an `Origin`/`Host` allowlist against rebinding, and keep the public MCP listener ignorant of GUI routes; no password or login page is exposed to the internet, and the GUI's origin never receives MCP traffic. The fallback is a **same-origin cookie session** on a separate hostname behind Cloudflare Access: a Hono-served login (reusing the passkey from the OAuth server once it exists) sets a `__Host-` cookie, the SPA calls a cookie-only prefix such as `/admin/api/...` that maps onto the same handlers, `/v1/banks/...` and `/mcp` never accept the cookie, every unsafe method gets an explicit `Sec-Fetch-Site: same-origin` or exact-`Origin` check plus a required header such as `X-Mem-CSRF: 1`, and erase and export demand re-authentication. If the GUI ever uses OAuth, it should be a BFF with tokens kept server-side, never a browser public client. `@hono/node-server`'s `serve()` currently binds Node's default host, so either design needs a small change in `main.ts`, and whether one `serve()` call can bind two listeners was not checked.

## Native Postgres, launchd and Haiku 5.5 make `mem` an appliance for a few dollars a month

### Auto-start: native Postgres under `brew services` removes the Docker race

The fewest moving parts come from running Postgres natively and supervising Node with launchd, macOS's service manager. Per-user agents live in `~/Library/LaunchAgents`; `RunAtLoad` starts a job once at load, `KeepAlive` set to true restarts it "unconditionally" (its dictionary form keys on `SuccessfulExit`, `Crashed` and more, while `NetworkState` "is no longer implemented"), `WorkingDirectory`, `EnvironmentVariables` and `StandardOutPath`/`StandardErrorPath` set the job's environment and logs, jobs are throttled to one spawn every ten seconds by default, launchd jobs must not daemonize, and for scheduled jobs `StartCalendarInterval` runs a missed slot "the next time the computer wakes up" while a `StartInterval` slot that falls during sleep "will be missed" ([launchd.plist(5)](https://keith.github.io/xcode-man-pages/launchd.plist.5.html)). `launchctl bootstrap|bootout gui/<uid>` loads and unloads agents, `kickstart -k` restarts one, `enable`/`disable` persist across boots, and `load`/`unload` are legacy ([launchctl(1)](https://keith.github.io/xcode-man-pages/launchctl.1.html)); a launchd job inherits no shell environment and no `~` expansion (secondary: [StackHarbor](https://stackharbor.com/en/knowledge-base/openclaw-as-launchd-service/)). `npm start` runs `node --env-file-if-exists=.env --import tsx src/attachment/rest/main.ts` on port 8787 against Postgres on host port 5433 ([package.json](file:///Users/blackpr/code/mem/package.json); [docker-compose.yml](file:///Users/blackpr/code/mem/docker-compose.yml)). `brew services start` starts a formula now and registers it at login (or at boot with `sudo`) ([Homebrew manpage](https://docs.brew.sh/Manpage)); `postgresql@17` is at 17.11, keg-only, with its data in `$HOMEBREW_PREFIX/var/postgresql@17` and a deprecation date of 2029-11-08 ([formulae.brew.sh postgresql@17](https://formulae.brew.sh/formula/postgresql@17)); and `pgvector` 0.8.7 has Apple Silicon bottles for the current macOS releases and builds against `postgresql@17` and `@18` ([formulae.brew.sh pgvector](https://formulae.brew.sh/formula/pgvector)).

If Docker stays, three things are missing today. Docker Desktop's "Start Docker Desktop when you sign in" is **disabled by default**, and container data lives in the disk image of its Linux virtual machine (VM) ([Docker Desktop settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/)); Resource Saver stops the VM only when no containers run, so it does not affect a running `mem-db` ([Resource Saver](https://docs.docker.com/desktop/use-desktop/resource-saver/)); restart policies default to `no`, apply only after a container has been up ten seconds, and `unless-stopped` leaves a manually stopped container down ([Docker restart policies](https://docs.docker.com/engine/containers/start-containers-automatically/)); and `mem`'s `db` service has **no `restart:` key** while `npm run db:down` runs `docker compose down`, which deletes the container though not the `mem-db-data` volume ([docker-compose.yml](file:///Users/blackpr/code/mem/docker-compose.yml); [package.json](file:///Users/blackpr/code/mem/package.json)). Docker Desktop is free for personal use and small businesses under 250 employees and $10M revenue ([Docker Desktop license](https://docs.docker.com/subscription/desktop-license/)). Colima autostarts with `brew services start colima`, keeps container data on a separate disk from v0.9.0, and does not document restart-policy behaviour ([Colima FAQ](https://github.com/abiosoft/colima/blob/main/docs/FAQ.md)), with one guide advising a manual first start before handing it to launchd ([NJ innovation guide](https://newjersey.github.io/innovation-engineering/guides/development/colima/)); OrbStack is free for personal use and $8 per user per month for business ([OrbStack pricing](https://orbstack.dev/pricing)), caps memory at 8 GB by default ([OrbStack settings](https://docs.orbstack.dev/settings)), and fixed its login auto-start in v1.6.4 without documenting the setting ([OrbStack release notes](https://docs.orbstack.dev/release-notes)).

The recommended combination is `brew services start postgresql@17` with the pgvector bottle; a one-time `pg_dump -Fc` from `mem-db` restored into the Homebrew cluster (which doubles as the first restore test, after checking that the bottle's pgvector is at least the container's `extversion`); `port = 5433` or a new `DATABASE_URL`; and a LaunchAgent labelled, say, `dev.mem.server` whose `ProgramArguments` run `/bin/zsh -c 'until pg_isready -h 127.0.0.1 -p 5433 -q; do sleep 2; done; exec /Users/blackpr/.nvm/versions/node/v22.17.0/bin/node --env-file-if-exists=.env --import tsx src/attachment/rest/main.ts'` with absolute paths, `WorkingDirectory` at the repo, an explicit `PATH`, `RunAtLoad` and `KeepAlive`, a `ThrottleInterval` of 10–30 seconds, and logs under `~/Library/Logs/mem/` (an untested sketch; the nvm path breaks on Node upgrades, and the `/opt/homebrew` prefix should be confirmed with `brew --prefix`). Both then come up at login with no VM and no readiness race, and simply resume after sleep. If Docker stays, enable start-at-sign-in, add `restart: unless-stopped` (or `always`) to `db`, use `docker compose stop` rather than `db:down` day to day, and keep the wait-for-Postgres loop. Clock drift and network re-attach for Docker or Colima VMs after sleep, and how macOS's "Background Items Added" approval treats user agents, were not researched.

### Backups make erasure a promise with an expiry date

`pg_dump` "makes consistent backups even if the database is being used concurrently" without blocking readers or writers; `-Fc` produces a compressed custom archive for selective restore with `pg_restore`; parallel dumps need the directory format; roles need `pg_dumpall`; and `--no-owner` and `--clean --if-exists` make restores portable ([pg_dump (PG 17)](https://www.postgresql.org/docs/17/app-pgdump.html)). restic always encrypts, and "Losing your password means that your data is irrecoverably lost"; it recommends B2's S3-compatible API over its native one, uses generic S3 settings for R2, and needs key-based login for SFTP ([restic: preparing a repo](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html)); `forget --keep-daily/--keep-weekly --prune` removes old snapshots and the data only they referenced, locking the repository while it runs ([restic: forget](https://restic.readthedocs.io/en/stable/060_forget.html)). For a few gigabytes, Backblaze B2 charges $6.95/TB/month with the first 10 GB free and free egress up to three times stored, though its page shows "© 2024" and no effective date, so the price is possibly stale ([B2 pricing](https://www.backblaze.com/cloud-storage/pricing)); Cloudflare R2 charges $0.015/GB-month with 10 GB-month, a million Class A and ten million Class B operations free and no egress fees (updated 2026-10-26: [R2 pricing](https://developers.cloudflare.com/r2/pricing/)); and a Hetzner Storage Box BX11 is 1 TB for €3.20 a month plus an unstated setup fee, speaks SFTP, rsync, Borg and restic, and keeps ten manual and ten automated snapshots in Germany or Finland ([Hetzner Storage Box](https://www.hetzner.com/storage/storage-box/)).

The daily job is a LaunchAgent with `StartCalendarInterval` running `docker exec mem-db pg_dump -U mem -d mem -Fc` (no `-t`, so no terminal mangles the binary) or, after the move, `pg_dump -h 127.0.0.1 -p 5433 -U mem -Fc -f ...`; then `restic backup`, `restic forget --keep-daily 7 --keep-weekly 4 --prune`, a weekly `restic check`, and a success ping to a dead-man's switch; the restic password lives in the Keychain with a second copy off the Mac. On R2 or B2 this costs about nothing; a Hetzner box is €3.20 flat, but its snapshots would keep pruned data longer, and whether B2 keeps old object versions after restic prunes (which would lengthen the erasure window) was not checked. A monthly restore test creates a scratch database, runs `pg_restore --no-owner --exit-on-error`, compares per-table counts recorded at dump time, runs `mem`'s paged hash-chain verification and re-verifies an erasure receipt or two with `verify-receipt`, then drops the database ([STATUS.md](file:///Users/blackpr/code/mem/STATUS.md)); storing the audit chain's head hash beside each dump lets a restore prove it is not a truncated or forked chain.

Backups interact directly with `mem`'s erasure receipts. The UK regulator, the ICO (Information Commissioner's Office), says a valid erasure request reaches backups too, but data may "remain within the backup environment for a certain period of time until it is overwritten" provided it is put "beyond use" and replaced "in line with an established schedule", and "You must be absolutely clear with individuals as to what will happen to their data", within one month; the page is under review because of the Data (Use and Access) Act ([ICO right to erasure](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/individual-rights/right-to-erasure/)). Its storage-limitation guidance says to delete from backups too where deletion is appropriate ([ICO storage limitation](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-protection-principles/a-guide-to-the-data-protection-principles/storage-limitation/)), and its processor-contract guidance accepts delayed backup deletion with safeguards (search summary: [ICO contracts](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/accountability-and-governance/contracts-and-liabilities-between-controllers-and-processors-multi/what-needs-to-be-included-in-the-contract/)). The EDPB (the board of EU data protection authorities) 2025 enforcement report on erasure, adopted February 2026 and about eight months old, says organisations that do not modify backups "should have appropriate procedures to keep track of erasure requests and comply with them on restored systems", criticises relying on overwrite cycles alone, recommends being able to "verify that erasure has been carried out and be able to demonstrate such erasure", and notes practices such as overwriting with random strings ([EDPB CEF 2025 report](https://www.edpb.europa.eu/system/files/2026-02/edpb_cef-report_2025_right-to-erasure_en.pdf)). For a purely personal system the UK GDPR (the UK's version of the EU General Data Protection Regulation) probably does not apply at all, since household processing is out of scope rather than exempt (search summaries: [ICO exemptions guide](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/exemptions/a-guide-to-the-data-protection-exemptions/); [ICO: who does the UK GDPR apply to](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/personal-information-what-is-it/who-does-the-uk-gdpr-apply-to/)), so the receipt is a product promise rather than a legal duty. Keeping that promise honest means stating the window in the receipt ("erased from the live store at T; encrypted backups containing it expire by T + 35 days"), keeping an append-only erasure ledger outside the dumps (bank, receipt id and hash, time, no content), and making "replay every erasure newer than the dump, then re-verify receipts" a mandatory step before a restored server takes traffic. A per-bank data key destroyed at erasure (crypto-shredding) would be stronger, but is a larger change.

### Health checks: a local watchdog, a session-start hook, and an external probe for the public URL

Claude Code is not silent when `mem` dies mid-session: a failed first connection is retried three times and then marked failed, a dropped server is retried five times with exponential backoff before the user sees `MCP server "<name>" disconnected · open /mcp to reconnect`, and `claude mcp list` shows `✔ Connected`, `! Needs authentication` or `✘ Failed to connect`; but at startup only servers needing authentication produce a notice, so a dead server is easy to miss ([Claude Code MCP](https://code.claude.com/docs/en/mcp)). A `SessionStart` hook (matchers `startup`, `resume`, `clear`, `compact`, `fork`) adds its plain stdout to Claude's context, while exit code 2 shows stderr to the user only; hooks default to a 600-second timeout and should be fast, and whether a JSON `systemMessage` is shown at session start was not confirmed ([Claude Code hooks](https://code.claude.com/docs/en/hooks)). claude.ai rejects private, loopback, CGNAT and IPv6-only hostnames with "Couldn't reach", attributes "works in Claude Code or curl but not claude.ai" to a non-routable server, and shows "Unexpected error while invoking tool" with an `ofid_` reference on failed calls ([claude.com connector troubleshooting](https://claude.com/docs/connectors/building/troubleshooting)); what it shows mid-conversation when a connected server disappears is undocumented. ChatGPT's behaviour has no official page; community threads report 424 "TaskGroup" errors at creation with the endpoint never contacted and tools that list but never reach the server (anecdotal: [OpenAI community: 424 TaskGroup](https://community.openai.com/t/mcp-connector-creation-fails-with-424-taskgroup-error-endpoint-never-contacted/1357635); [OpenAI community: resource not found](https://community.openai.com/t/mcp-connector-resource-not-found-tools-call-never-reaches-server/1370632)), and third-party guides disagree on plans (secondary: [gofastmcp ChatGPT](https://gofastmcp.com/v3/integrations/chatgpt); [Boomi guide](https://help.boomi.com/docs/Atomsphere/Platform/Connect_chatgpt_setup)).

Three layers cover this. A LaunchAgent with `StartInterval` 60 runs `curl -fsS --max-time 2 http://127.0.0.1:8787/healthz` and on failure posts a macOS notification once per outage through AppleScript's `display notification` ([Apple Mac Automation Scripting Guide](https://developer.apple.com/library/archive/documentation/LanguagesUtilities/Conceptual/MacAutomationScriptingGuide/DisplayNotifications.html)). A Claude Code `SessionStart` hook in `~/.claude/settings.json`, matcher `startup|resume`, curls the same URL with a two-second cap and, on failure, prints "mem is DOWN: recall/retain will fail. Restart: launchctl kickstart -k gui/$(id -u)/dev.mem.server" to stdout with exit 0, so Claude knows to tell the user and skip `recall` (exit 2 would warn only the human). A free external monitor watches the public URL, where "down because the Mac sleeps" is a true positive: Healthchecks.io's free tier has 20 checks and suits the backup job as a dead-man's switch with a one-day grace ([Healthchecks.io pricing](https://healthchecks.io/pricing/)), Better Stack's free tier has 10 monitors and a status page with an unstated interval ([Better Stack pricing](https://betterstack.com/pricing)), and self-hosted Uptime Kuma (MIT, 20-second intervals, 90+ notification services) helps only if it runs somewhere other than the Mac ([Uptime Kuma](https://github.com/louislam/uptime-kuma)). `/healthz` should also gain a readiness variant that runs `SELECT 1` and checks extraction-queue depth, since a liveness probe that never touches Postgres reports a server with a dead database as healthy.

## Retain less, and retain the user's words: a policy built from vendors' rules and Mem0's failures

### The big assistants share one policy shape

ChatGPT, Claude and Gemini all combine an always-honoured explicit path ("remember that ...") with a narrow implicit path whose test is durability, an exclusion list, and after-the-fact review rather than approval. The newest leaked ChatGPT memory-tool prompt (stating 2025-09-29 as its date; unofficial and possibly stale) tells the model to save whenever the user asks to save, remember, forget or delete, and "Anytime the user shares information that will likely be true for months or years", with "from now on" and "going forward" as signals; to call the tool before saying "noted"; not to save "Overly-personal details that could feel creepy", "Short-lived facts that won't matter soon", "Random details that lack clear future relevance", "Redundant information that we already know about the user", or content "pulled from text the user is trying to translate or rewrite"; to skip sensitive categories (race, religion, precise location, politics, health, sex life) unless explicitly asked; and, when unclear, to "ask the user for clarification" ([Zei33 gist](https://gist.github.com/Zei33/415224187a1632f78e959a2e57ad838c)). Earlier 2025 leaks were blunter ("DO NOT SAVE SHORT TERM INFORMATION.", "DO NOT USE THE BIO TOOL TO SAVE SENSITIVE INFORMATION."; unofficial, possibly stale, search snippets: [r/PromptEngineering, Mar 2025](https://redlib.ssps.io/r/PromptEngineering/comments/1j5mca4/i_made_chatgpt_45_leak_its_system_prompt); [r/PromptEngineering, May 2025](https://redlib.ssps.io/r/PromptEngineering/comments/1kseb8o/just_made_gpt4o_leak_its_system_prompt/mtm0h65/?context=3)). Officially, OpenAI's 2025-10-15 notes describe automatic management that keeps relevant memories "top of mind" and pushes others to the background by recency and frequency, with manual prioritization (possibly stale, search snippet: [ChatGPT release notes](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)); the Memory FAQ returned 403 ([Memory FAQ](https://help.openai.com/en/articles/8590148-memory-in-chatgpt-remembering-what-you-chat-about)); and users still report "memory full" warnings, one at a 73–74 KB list (anecdotal: [OpenAI community](https://community.openai.com/t/please-increase-the-capacity-of-legacy-saved-memories/1394689); [OpenAI community](https://community.openai.com/t/memory-full-chatgpt-memory-is-full-you-can-forget-existing-memories-to-make-space/1213437)).

Claude saves "individual topics during chats", on its own and on request, focused on role and professional context, people and places in the user's work, communication and technical preferences, and ongoing projects, with sensitive topics opt-in and a never-save list ([Claude Help Center](https://support.claude.com/en/articles/11817273); [search summary of same article](https://support.claude.com/en/articles/11817273-using-claude-s-chat-search-and-memory-to-build-on-previous-context)). Claude Code's auto memory keeps four typed kinds of note (`user`, `feedback`, `project` decisions "that Claude can't derive from the code or git history", and `reference`), skips anything derivable from the codebase ("architecture, file paths, or debugging fixes") or already in CLAUDE.md, "doesn't save something every session", always saves "remember that ..." requests, caps its always-loaded index at 200 lines or 25 KB with reminders to "merge or drop stale entries", and shows "Saved 2 memories" in the UI ([Claude Code docs: memory](https://code.claude.com/docs/en/memory)). Anthropic's API memory tool is task-progress oriented ("record status / progress / thoughts"), suggests scoping with "Only write down information relevant to <topic>", admits "Claude usually refuses to write sensitive information to memory files. For stronger guarantees, add validation that strips sensitive data", and recommends size caps and deleting memory not accessed for a long time ([Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). Gemini's Saved Info is documented as explicit only, filled when the user adds items or asks, refusing content that breaks its prohibited-use policy ([Gemini Apps Help](https://support.google.com/gemini/answer/16413516)), while past-chat memory was reportedly renamed "Memory" in March 2026 (unofficial, search snippet: [ai-toolbox guide](https://www.ai-toolbox.co/gemini-management-and-productivity/gemini-memory-saved-info-2026)). Against that shape, `mem`'s current instruction ("durable ... a decision, a preference, a change") lacks an explicit exclusion list, a redundancy rule, a sensitive-category rule and an "ask when unclear" rule; Claude Code's "skip what the code already says" is the coding-session analogue of "skip transient task details". No vendor publishes how often it saves.

### Mem0's 97.8% junk audit names the failure modes

The best public evidence on over-saving is one deployment's audit of Mem0 (opened 2026-03-27, closed 2026-06-05; anecdotal, one human and one agent over 32 days): of 10,134 entries, about 224 survived, a **97.8%** junk rate (96.9% in a 6,264-entry manual pass, 89.6% in a final Claude Sonnet 4.6 batch after 20 days on gemma2:2b) ([mem0 #4573](https://github.com/mem0ai/mem0/issues/4573)). The junk was boot-file and system-prompt restating (about 3,200 entries, 52.7%), heartbeat and cron noise (11.5%), architecture dumps (8.2%), transient task state (7.4%), hallucinated user profiles (5.2%), identity confusion (3.3%), security and privacy leaks (2.1%), wrong locations and fabricated lifestyles; and the most damaging failure was a **feedback loop**, 808 entries saying "User prefers Vim" (191 exact copies) though nobody used Vim, because recalled memories were re-extracted as new facts. The author concluded "The extraction prompt is the bottleneck, not the model", since a stronger model extracted more faithfully and therefore more indiscriminately, and proposed marking recalled memories, a quality gate before storage, negative examples, a REJECT action, user-only and identity-aware extraction, and dropping system and unconfirmed assistant content. After four config changes a 48-hour sample was still 46.6% junk, and a commenter's write-time gate cut stored junk 45% at 30 days with no recall loss across 18 runs (2026-09-16), while true-but-never-asked facts survived at 90 days (anecdotal). The closing comment cited ADD-only extraction (April 2026), decay (May) and temporal reranking (June) and left prompt permissiveness, loop prevention and identity awareness as "ongoing areas of improvement" (all [mem0 #4573](https://github.com/mem0ai/mem0/issues/4573)); related issues propose a faithfulness check before writes (2026-09-11) and report ADD-only extraction surfacing stale or contradictory facts (2026-04-24) ([mem0 #7283](https://github.com/mem0ai/mem0/issues/7283); [mem0 #4956](https://github.com/mem0ai/mem0/issues/4956)).

The frameworks' own guidance agrees. Mem0's docs say to state the exact allowed fact types, include negative few-shots that return `{"facts": []}` (greetings, small talk, off-domain statements), warn that "Overly broad prompts let unrelated facts through", and recommend regression samples and versioned prompts ([Mem0 docs: custom fact extraction](https://docs.mem0.ai/open-source/features/custom-fact-extraction-prompt)); its platform takes plain-text `includes`/`excludes` and 15 replaceable default categories applied at ingestion, with sources conflicting on per-call overrides (search snippets: [Mem0 selective memory](https://docs.mem0.ai/platform/features/selective-memory); [Mem0 custom categories](https://docs.mem0.ai/platform/features/custom-categories)). Graphiti invalidates outdated facts and keeps them as history ([Zep vs Graphiti](https://help.getzep.com/zep-vs-graphiti); possibly stale, January 2025: [Zep paper](https://arxiv.org/pdf/2501.13956.pdf)), and Zep Cloud reportedly rates facts for relevance with high, medium and low examples to filter at retrieval (search snippet from a third-party mirror, field names unverified: [n8n Zep node mirror](https://frontend-f26.pages.dev/package/n8n-nodes-zep/zep/Graph:Update%20Graph)). Letta's 2025-04-21 sleep-time agents edit memory in the background with a stronger, slower model because incrementally formed memories "may become messy and disorganized over time" (possibly stale: [Letta blog: sleep-time compute](https://letta.com/blog/sleep-time-compute)), current Letta Code "Dreaming" consolidates after N steps or on compaction with an optional, costlier review step ([Letta docs: sleep-time](https://docs.letta.com/guides/agents/architectures/sleeptime)), and a community guide lists merging, deduplication and pruning as consolidation tasks (anecdotal, search snippet: [Letta forum](https://forum.letta.com/t/sleeptime-agents-for-memory-consolidation-best-practices-guide/154)). LangMem says hot-path writes "add perceptible latency", background extraction after inactivity gives "higher recall", over-extraction "could lead to reduced precision", and a single schema'd profile avoids "extraneous information" (undated, possibly stale: [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)). Supermemory filters at ingestion with a `filterPrompt` and, since a June 2026 changelog, a per-space "what to remember" context (search snippets: [Supermemory customization](https://supermemory.ai/docs/concepts/customization.md); [Supermemory rules](https://supermemory.ai/docs/concepts/rules)), and queues inferred memories for approve, decline or undo ([Supermemory memory review](https://supermemory.ai/docs/recall/memory-review)).

`mem` already blocks the two largest Mem0 junk sources by construction, since it extracts only from user-authored text, and its triage skips acknowledgements, code-only turns, stack traces and contentless JSON. Its remaining exposure is transient task state, hallucinated or identity-confused profiles, and above all the **recall-to-retain loop over MCP**: a model that has just seen `recall` output can paraphrase it back into `retain`, and `mem` cannot verify authorship on claude.ai, ChatGPT or Gemini, so the server needs its own guard.

### Wording matters, `instructions` are only a hint, and hooks are deterministic

Anthropic advises describing a tool as "to a new hire on your team" and says "Even small refinements to tool descriptions can yield dramatic improvements", citing its SWE-bench result and a fix that stopped Claude appending "2025" to searches, and recommends few non-overlapping tools evaluated with realistic tasks and tool-call counts (2025-09-11, possibly stale: [Anthropic: Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)). In the spec, server `instructions` are "like a 'hint' to the model" that "MAY be added to the system prompt", and annotations are "hints ... not guaranteed" that clients should not trust from untrusted servers, with the spec's own `openWorldHint` example calling a memory tool closed-world (spec 2025-06-18; later revisions exist: [MCP schema 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/schema)). A 2026 study of 856 tools on 103 servers found 97.1% of descriptions have at least one "smell" and 56% fail to state their purpose clearly; augmenting descriptions raised median task success 5.85 points and partial completion 15.12%, but **raised execution steps 67.46%** and regressed in 16.67% of cases, while compact combinations kept reliability with fewer tokens (v1 2026-02-16, v3 2026-05-31: [arXiv 2602.14878](https://arxiv.org/abs/2602.14878)); a companion study of 10,831 servers defines 18 smell categories (search snippet: [arXiv 2602.18914](https://arxiv.org/abs/2602.18914v1)); and a paper on deliberate description optimization was found but not read ([arXiv 2605.23916](https://arxiv.org/pdf/2605.23916)). Claude Code calls CLAUDE.md and memory "context, not enforced configuration", says "The more specific and concise your instructions, the more consistently Claude follows them", and recommends hooks for anything that must happen, since they run "regardless of what Claude decides" ([Claude Code docs: memory](https://code.claude.com/docs/en/memory)). Ask-first and explicit-trigger patterns ship in all three products ([Zei33 gist](https://gist.github.com/Zei33/415224187a1632f78e959a2e57ad838c); [Claude Code docs: memory](https://code.claude.com/docs/en/memory); [Gemini Apps Help](https://support.google.com/gemini/answer/16413516)). No controlled study measures memory-tool call frequency under different wordings, so the decisive rule must sit compactly in the `retain` description itself, repeated in `instructions`, and `mem` needs its own replay eval to know how often each client calls it.

Claude Code's hooks give deterministic capture points: `SessionStart` (startup, resume, clear, compact, fork) and `UserPromptSubmit` (30-second default, exit 2 blocks the prompt) inject stdout or `additionalContext`; `Stop` carries `transcript_path` and `last_assistant_message`; `PreCompact` can block compaction; `SessionEnd` cannot inject and all its hooks share a 1.5-second budget (raisable to 60 per hook); and handlers can be `command` (with `async: true`), `http`, `mcp_tool` (calling a configured MCP server's tool directly), `prompt` or an experimental `agent` ([Claude Code hooks](https://code.claude.com/docs/en/hooks)). Open-source plugins built on them capture whole sessions: claude-mem (v15.4.0, about 104k stars) uses six hooks to record tool observations and AI-compressed summaries, injects context at session start, and honours `<private>` tags ([claude-mem](https://github.com/thedotmack/claude-mem)), and on Gemini CLI uses SessionEnd and SessionStart (search snippet: [claude-mem Gemini CLI setup](https://docs.claude-mem.ai/gemini-cli/setup.md)). Its costs, all anecdotal or competitor claims, include about 5,150 compression tokens per session with hooks firing on nearly every action ([dev.to](https://dev.to/harrisonsec/agent-memory-is-a-cache-coherence-problem-4jmk)), an A/B at equal $5.56 cost but more than doubled first-prompt cache reads from SessionStart injection (2026-03-14: [Reddit snapshot](https://reddit.sentinel-team.org/posts/1rsh7oi/snapshots/2026-03-14T00%3A11%3A38.395735Z)), a claimed 42k tokens of plugin context per session ([claude-historian comparison](https://glama.ai/mcp/servers/@Vvkmnn/claude-historian/blob/5523c7a4febebd9cb3e54990eb6bc693ee206aa5/COMPARISON.md)), an LLM-judged keep/skip decision that a lighter fork replaced with deterministic filters ([claude-mem-lite](https://awesome.ecosyste.ms/projects/github.com%2Fsdsrss%2Fclaude-mem-lite)), and 50–200 ms per tool-call hook plus code-upload and cross-project leak risk ([tutorial](https://openclaweco-website-build.pages.dev/tutorial/claude-memory-tutorial/lesson-10/)). Codex CLI added experimental SessionStart, Stop and UserPromptSubmit hooks in v0.114.0 (March 2026) behind a flag (search snippet; the article returned 404: [Codex hooks deep dive](https://codex.danielvaughan.com/2026/03/26/codex-cli-hooks-deep-dive); official page not read: [OpenAI docs: hooks](https://developers.openai.com/es-419/docs/hooks)); Hindsight's Codex integration recalls on UserPromptSubmit, retains whole sessions on Stop keyed by session ID, and later filtered synthetic AGENTS messages ([Hindsight Codex changelog](https://hindsight.vectorize.io/changelog/integrations/codex)); Gemini CLI gained SessionStart and SessionEnd in v0.26.0 (search snippets: [Gemini CLI hooks reference, mirror](https://www.mintlify.com/google-gemini/gemini-cli/reference/hooks); [hook comparison](https://lilting.ch/en/articles/gemini-cli-hooks-research)); and `mem`'s own spike measured Hindsight spending 1.09M LLM tokens to write one 64-turn conversation (`/Users/blackpr/code/mem/STATUS.md`). Cursor's hooks were not researched.

Batching and review have precedents too. LangMem and Letta trade freshness for recall and latency ([LangMem](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/); possibly stale: [Letta blog](https://letta.com/blog/sleep-time-compute); [Letta docs](https://docs.letta.com/guides/agents/architectures/sleeptime)); claude.ai moved the other way, from a 24-hour synthesis to in-chat saves ([Claude Help Center](https://support.claude.com/en/articles/11817273)); ChatGPT deprioritizes rather than deletes (possibly stale, search snippet: [ChatGPT release notes](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)); Mem0 added recency-aware decay in May 2026 ([mem0 #4573](https://github.com/mem0ai/mem0/issues/4573)); Anthropic recommends expiring untouched memory files ([Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)); Claude Code enforces a hard index budget ([Claude Code docs: memory](https://code.claude.com/docs/en/memory)); and review queues exist in Supermemory ([Supermemory memory review](https://supermemory.ai/docs/recall/memory-review)), in Automation Anywhere and Odin, which hold detected memories as pending for admin approval with the triggering message and a confidence score and expire them after seven days (search snippets: [Automation Anywhere](https://ai-kb.automationanywhere.com/agents/memory-managing); [Odin](https://learn.getodin.ai/agents/memory-managing)), and in memsmith's `PendingConfirmation` state (search snippet: [memsmith](https://pypi.org/project/memsmith/)). No major consumer assistant gates memory behind approval, and no data exists on review fatigue or on per-message versus end-of-session extraction quality. `mem`'s extract-v3 averages 11,629 input tokens and about 0.055 USD per session-sized call on Opus 5.5, with uncached context the next cost lever ([eval/RESULTS.md](file:///Users/blackpr/code/mem/eval/RESULTS.md); [STATUS.md](file:///Users/blackpr/code/mem/STATUS.md)).

### Recommended policy: strict and model-initiated on chat apps, batched with review in Claude Code

Three options are supported by the evidence, and the recommendation combines two of them. **Option A**, model-initiated retain with a strict policy and server-side guards, is the ChatGPT and Claude pattern and the only one that works on all four clients; its weakness is that compliance varies by model and is unmeasured. **Option B**, explicit-only retain, is the Gemini Saved Info pattern: highest precision, near-zero junk, 0–2 calls a day, but it misses durable facts mentioned in passing and would make `mem` feel weaker than the built-in memories. **Option C**, a hook-driven end-of-session batch in Claude Code, is deterministic and gives the extractor a whole session to judge durability, but works only in the CLIs, yields little from code-heavy sessions, carries secrets and private code that `mem`'s secret detection and a `<private>`-style opt-out must handle, and adds review work. A per-prompt capture hook that sends every user message to `retain` is the Mem0 firehose and should not be built.

The retain policy for the chat apps is Option A with B's explicit override, written compactly into the `retain` description (and repeated in `instructions`, first 512 characters for ChatGPT, under 4,096 for Claude Code): call it **always** when the user asks to remember or forget something; otherwise **only** for statements likely to stay true for months, meaning decisions, preferences, and changes to the user's tools, people, places and projects; **never** for the current task's steps, code, errors, the assistant's own words, facts just returned by `recall`, text the user is translating or editing, or health, religion, politics, ID and financial numbers unless explicitly asked; **pass the user's own words verbatim**; **ask if unsure**; and **never say "noted" without calling `retain`**. Behind it, the server rejects or no-ops a retain whose content mostly restates currently believed facts (the loop guard), drops exact duplicates within a session, applies a soft per-session cap, and records `rejected:<reason>` in the ledger, so rejection is visible in the GUI rather than silent. In Claude Code, add Option C: a `SessionEnd` (and `PreCompact`) hook with an `async` command or `mcp_tool` handler that only enqueues the session's user-authored turns, excluding injected recall and system-reminder blocks, as one episode batch; one extraction call judges the whole session; its facts land as `candidate`, excluded from recall or returned flagged, reviewed in the GUI or through `list_facts`, `confirm_fact` and `dispute_fact`, and expired after about seven days unless confirmed or restated. `UserPromptSubmit` is the natural place to inject recall, but anything injected must be excluded from later extraction. Decay belongs in ranking, not deletion, because true-but-unused facts should survive. Expected volume is an estimate only: zero to three retains per conversation and well under 1 USD a day on Opus prices even before switching models, plus five to fifteen session batches a day for a heavy Claude Code user.

The apps themselves cap the risk of spam, at the cost of friction. ChatGPT and Gemini use `mem` only when the user picks it with `@` and confirm every write (ChatGPT remembers approval only within a conversation), Claude lets the owner set `retain` to "Always allow" per tool, and Microsoft's orchestrators decide from the description alone, so in practice `recall` should be frictionless (read-only annotations) and `retain` deliberate. The built-in memories will keep learning in parallel; the owner either pauses them and treats `mem` as the system of record, pushing a curated subset back into Claude and Gemini through their paste-import boxes, or accepts two drifting memories.

## Conclusion

The vendor-facing half of this project has quietly become standard plumbing. Under the current spec, Claude, ChatGPT and the coding tools converge on the same handful of mechanisms (a 401 that points at path-specific resource metadata, PKCE, an audience-bound token, and a client identified by the URL of its own metadata document), so a single-user authorization server needs almost no client database and no per-vendor code, with dynamic registration kept only for Gemini and the Microsoft surfaces; the remaining uncertainty is empirical, not architectural, because no public report yet shows claude.ai or ChatGPT completing that flow against either candidate library and Gemini's redirect URI is undocumented, so a one-evening spike against a throwaway bank is worth more than further reading. The same convergence changes the threat model in a useful way: with exactly one person who can ever approve a client, the passkey and a consent page that truthfully names the redirect host are the whole perimeter, which is also the argument for keeping the GUI, with its erase and export buttons, off the public internet entirely.

The owner-facing half is where `mem` differs from everything it competes with, and the daily-driver move sharpens three of its promises. Privacy becomes a question of increments rather than absolutes: every chat app already receives recalled memories into its model's context, so what a tunnel provider adds by decrypting traffic is the cross-app, cross-bank aggregate, which is real but bounded and is a fair price for a hostname that survives the move to a VPS. Erasure becomes a promise with an expiry date once encrypted backups exist, and stating that date in the receipt, then replaying erasures after any restore, is what keeps "provably deleted" honest. And with Haiku-class pricing, extraction stops being the cost that matters; the scarce resource becomes measurement, since neither the 40-question extractor check nor any public benchmark can see a difference smaller than several questions, and nothing yet measures how often each client calls `retain`. The money saved on the model is best spent on the 150-question extractor run and a transcript-replay eval of retain behaviour, because those two numbers, not the choice of stack, will show whether `mem` is better than the memories the apps already ship.
