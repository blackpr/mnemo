## Q1. Which front-end stacks are current, and how does each fit into one existing package?

### Takeaway
Every official scaffolder below (create-next-app, create-vite, @tanstack/cli, create-react-router, create-astro, create-hono) generates a standalone project with its own package.json. None of them adds a GUI to an existing package in place. The cheapest fit under the one-package rule is a Vite + React SPA built to static files that the existing Hono process serves (or Hono JSX + htmx, which needs no build step at all). Next.js, TanStack Start, React Router framework mode and Astro all bring their own server or build model, so in production they either need a second process or must be reduced to a static or SPA build, which throws away most of what makes them worth using.

**tsconfig mechanics (any stack)**
- TypeScript 7.0 (2026-07-08) is the native Go port. `tsc --build` and project references are supported. It "does not ship with an API" (expected in 7.1). New defaults: `strict: true`, `types: []`, `module: esnext`. **`baseUrl`, `moduleResolution: node/node10` and `classic` are now hard errors.** Tools that need the API (typescript-eslint, Volar-based Astro tooling) should stay on 6.0 through the `@typescript/typescript6` alias. — [TypeScript blog: Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)
- Project references: a referenced config can be "a path to a config file with any name". Referenced projects need `composite` (which forces `declaration`). - When `lib` is unset, TypeScript's default includes browser definitions "like `document`". So mem's current tsconfig, which sets no `lib`, already has DOM types, even though it restricts `@types` to node. — [TSConfig: lib](https://www.typescriptlang.org/tsconfig/lib.html)

### Inferences
- **Scaffold-into-subfolder-then-merge works for Vite and is awkward for the rest.** Running `npm create vite@latest web -- --template react-ts` creates `web/package.json`. Merging means moving react, react-dom, vite, @vitejs/plugin-react and the @types packages into the root package.json, deleting `web/package.json`, and pointing `vite.config.ts` at `root: 'web'`. Only one Vite config and one tsconfig pair need to move. Next.js expects `app/`, `next.config.*`, `next-env.d.ts` and `tsconfig.json` at its project root. TanStack Start and React Router expect their Vite plugin config and route tree at the package root. Merging those into mem's root would put framework config files next to the server's.
- **TypeScript version is a real merge conflict.** The Vite template pins `typescript ~7.0.2`, while mem is on `^5.9.3`. One package gets one `typescript` devDependency. Moving the server to TS 7 means `types` now defaults to `[]` (harmless, since mem sets it), `strict` is already on, and NodeNext is fine. But any tool that needs the TS JS API (typescript-eslint, Astro's Volar tooling) would need the `@typescript/typescript6` alias. Keeping TS 5.9 for both is also viable (Vite only type-checks through `tsc -b`). This needs a decision before scaffolding.
- **A second tsconfig does not make a second package.** A `tsconfig.web.json` (DOM lib, `moduleResolution: bundler`, `jsx: react-jsx`, `noEmit`, `include: ["web"]`) next to the existing NodeNext `tsconfig.json`, with the existing config adding `"exclude": ["web"]`, is just two compiler configs in one package. TypeScript documents that config files can have any name. The `typecheck` script would become `tsc --noEmit && tsc -p tsconfig.web.json --noEmit`, or `tsc -b` with a solution file, though `-b` requires `composite`.
- **shadcn's documented `baseUrl` + `paths` edit fails on TS 7.** Under TS 7, use `paths` without `baseUrl` (paths resolve relative to the tsconfig since TS 4.1), or use `package.json#imports`, which shadcn's components.json explicitly accepts as an alias source (see Q2).
- **Hono RPC (`hc`) does not work today without refactoring the server.** `createApp()` returns the annotated type `Hono<Env>` and registers routes as statements. The schema type parameter is erased, so `typeof app` carries no routes. Using `hc` would mean rewriting the REST routes as a chained expression with typed validators (for example `@hono/zod-validator` or Standard Schema) and dropping the return-type annotation. The GUI tsconfig would also have to type-check server source, which pulls in `@types/node` and mem's strict flags. That is doable in one package, but it is the most invasive part of option (b). A thin hand-written `fetch` client over the existing JSON schemas (`src/attachment/rest/schemas.ts`) is the lower-cost alternative.
- **Process count.** In production, options (b), Hono JSX/htmx, and Next or React Router or TanStack Start reduced to static/SPA output all run as one process (Hono serving files). Next with its own server, TanStack Start through Nitro (`node .output/server/index.mjs`), React Router SSR and Astro SSR are second processes, unless they are mounted inside Hono through a fetch-handler bridge. That bridge is documented for TanStack's Rsbuild output with Express, but nowhere for Hono. In development, Vite-based options run a second dev server (5173) proxying `/v1` to Hono on 8787, unless `@hono/vite-dev-server` runs the Hono app inside Vite. Hono JSX + htmx has no dev server at all: `npm start` (tsx) serves it.
- **Node 22.17 is below several engines floors.** React Router 8 needs 22.22.0+ and Astro 7 needs 22.23.4+. Next's native-ESM `next.config.ts` is on by default only from 22.18. Vite 8, TanStack Start (22.12+) and Next itself (20.9+) work. Any option means bumping the local Node 22 minor or accepting engine warnings.
- **Ranking by fit to the owner's rules:**
  1. Vite react-ts SPA built into a folder served by `serveStatic`. One package, one prod process, battle-tested, official CLI.
  2. Hono JSX + htmx. Zero new build tooling and zero second process. It is not a "scaffold with the framework CLI" stack, and htmx 2 vs 4 is in transition.
  3. Next.js with `output: 'export'`. Works, but static export forbids the dynamic `facts/[id]` routes without `generateStaticParams`, so detail pages need query strings or client-side params. It also adds roughly 280 MB of Next plus SWC to a server package.
  4. TanStack Start or React Router 8 in SPA mode. Each is a framework whose server half goes unused.
  5. HonoX (alpha) and Astro (static-first, TS 6 tooling) are poor fits for an interactive admin tool.

## Q2. shadcn/ui: which stacks it supports, Tailwind v4, components.json, and subfolders

### Takeaway
shadcn/ui officially supports Next.js, Vite, TanStack Start, React Router, Astro and Laravel, plus manual React setups. New projects get Tailwind v4 and React 19. components.json is only needed for the CLI, and the CLI takes `-c/--cwd`, so it can run against a subfolder. Its built-in `--monorepo` mode is a multi-package Turborepo, which is exactly what the owner's rule forbids.

### Cited Findings
- The installation page lists guides for Next.js, Vite, TanStack Start, Laravel, React Router, Astro and React (Manual). `init -t` templates: `next`, `vite`, `start`, `react-router`, `astro`. The page has no date. — [shadcn: Installation](https://ui.shadcn.com/docs/installation)
- shadcn is at 4.23.0 (npm, 2026-10-27). 4.0.0 was published 2026-03-06. — [npm: shadcn](https://www.npmjs.com/package/shadcn)

Init "installs dependencies, adds the `cn` util and configures CSS variables" and adds `@import "shadcn/tailwind.css"`. — [shadcn: CLI](https://ui.shadcn.com/docs/cli)
- components.json is required only when using the CLI ("Copy-and-paste users don't need it"). "In a monorepo, run from `apps/web` or use `-c apps/web`." — [shadcn: Vite](https://ui.shadcn.com/docs/installation/vite)
- `init --monorepo` scaffolds `apps/web` and `packages/ui` workspaces with Turborepo, and "every workspace must have" its own components.json. — [shadcn: Monorepo](https://ui.shadcn.com/docs/monorepo)
- tailwindcss / @tailwindcss/vite are at 4.3.3 (npm, 2026-10-19). Tailwind 4.0.0 was published 2025-01-21. — [npm: tailwindcss](https://www.npmjs.com/package/tailwindcss)

### Inferences
- Under one package, the workable setup is a single `components.json` for the one GUI. It can sit at the package root, with `tailwind.css` pointing at `web/src/index.css` and aliases pointing into `web/`. Or it can sit in `web/` and be driven with `-c web`. Never use `--monorepo`.
- Using `package.json#imports` for the aliases (`"#web/*": "./web/src/*"`) avoids `baseUrl`, which TS 7 rejects. It also works with mem's NodeNext resolution and Vite. This looks like the cleanest alias choice for a single package.
- shadcn adds runtime dependencies to whichever package.json it detects (radix/base-ui primitives, `class-variance-authority`, `clsx`, `tailwind-merge`, `lucide-react`, `tw-animate-css`). In one package these sit next to the server's dependencies. Moving the GUI-only ones to devDependencies keeps the server's production install lean, because Vite bundles them at build time.

### Gaps
- No primary source confirms how `shadcn init -c web` behaves when `web/` has no package.json (whether it installs into the nearest parent package.json or errors). A dry run (`add --dry-run`) on a scratch copy would settle this, but that was out of scope.
- The shadcn pages carry no dates, so freshness is inferred from the npm release date (2026-10-27).

## Q3. Repo shapes against "one repo, one npm package, no monorepo"

### Takeaway
Shape 2 (the GUI built to static files and served by the same Hono process) is the only shape that keeps one repo, one package.json, one production process and one deployable. Shape 1 (Next.js inside the package) can keep one package.json if merged by hand, but it brings a second production process unless reduced to static export. Shape 3 (a separate repo) breaks the rule outright. npm workspaces are multi-package by definition, so they count as a monorepo under this rule.

### Cited Findings
- npm workspaces are "the set of features in the npm cli that provides support for managing multiple packages from your local file system". Each workspace is "a nested package folder with its own `package.json`", symlinked into root `node_modules`. The page does not use the word "monorepo". Docs are for npm CLI 11.21.1, last edited 2026-02-11. — [npm Docs: Workspaces](https://docs.npmjs.com/cli/v11/using-npm/workspaces)
- Every official scaffolder creates its own project folder: create-next-app "will create a folder with your project name" ([Next.js](https://nextjs.org/docs/app/api-reference/cli/create-next-app)); create-react-router takes a directory name ([React Router](https://reactrouter.com/start/framework/installation)); the create-astro wizard "will help create" a directory ([Astro](https://docs.astro.build/en/install-and-setup/)); create-vite accepts `.` for the current directory ([Vite](https://vite.dev/guide/)).
- Next.js does document manual installation into an existing project with three packages plus scripts. — [Next.js: Installation](https://nextjs.org/docs/app/getting-started/installation)
- Next's static export runs on "any web server that can serve HTML/CSS/JS static assets", but loses cookies, Server Actions, Proxy, rewrites/redirects/headers and request-dependent route handlers. — [Next.js: Static Exports](https://nextjs.org/docs/app/guides/static-exports)
- Next's own server (`next start`) or a custom server is a separate entry point. Custom servers are not compatible with standalone output. — [Next.js: Custom Server](https://nextjs.org/docs/app/guides/custom-server)
- Hono's monorepo guidance for RPC is to separate server and client projects (for example with Turborepo) and share `AppType` through project references. — [Hono: RPC](https://hono.dev/docs/guides/rpc)
- shadcn's monorepo mode is two workspaces under Turborepo. — [shadcn: Monorepo](https://ui.shadcn.com/docs/monorepo)

### Inferences
Verdict per shape:

| Shape | package.json files | Prod processes | Deployables | Breaks the rule? |
|---|---|---|---|---|
| (2) Vite (or Hono JSX/htmx) GUI, static files served by Hono `serveStatic` | 1 (after merging the scaffolded deps) | 1 | 1 (`npm start`; `npm run build:web` before start) | **No.** The only additions are a build step and a second tsconfig. Dev needs Vite on 5173 as a second dev-only process (or `@hono/vite-dev-server`). Hono JSX/htmx needs neither. |
| (1a) Next.js in the same package with `output: 'export'`, served by Hono | 1 if merged manually; 2 if `create-next-app` output is left in a subfolder | 1 | 1 | **Mildly.** Fine on paper, but Next's root-level conventions (`app/`, `next.config`, `next-env.d.ts`, `tsconfig.json` include) clash with the server's, and the static-export limits remove Next's main reasons to exist. |
| (1b) Next.js in the same package with its own server (`next start` or a custom server) | 1 if merged; 2 if not | **2** (Next on 3000 plus Hono on 8787), or 1 if Hono is rebuilt on a Node `http` custom server | 1 repo but 2 runtime services | **Moderately.** One package, but two processes, two ports, a reverse proxy or CORS between them, and Next's server becomes part of the security surface. |
| (1c) npm workspaces (`web/` plus the server) | **2+** | 1 or 2 | 1 or 2 | **Yes.** Workspaces are multiple packages under one root, which is a monorepo for this purpose. |
| (3) Separate repo | 2 (one per repo) | 2 (or static hosting plus Hono) | **2** | **Yes, outright.** Two repos and two deployables. A cross-origin GUI also forces CORS and cross-site cookie handling (SameSite=None) or bearer tokens in the browser, and Hono RPC types would have to be published or vendored. |

- "Two tsconfig files" and "a `web/` folder" are not a second package. Only a second package.json (or a workspaces field) is. A scaffolder's `web/package.json` must be deleted after merging, or shape 2 silently turns into shape 1c.
- The build output folder (for example `dist/web`) should be git-ignored and served by absolute path (`fileURLToPath(new URL(...))`), because `serveStatic` root is relative to `process.cwd()`. It must not overlap any route prefix that has auth middleware, because Hono warns that path-scoped middleware may not protect static files.

### Gaps
- No authoritative definition says whether "one package with two tsconfigs and two build tools" counts as a monorepo. The verdict above uses the owner's literal rule (one package.json, one repo).

## Q4. How the GUI should authenticate (single user)

### Takeaway
For a same-origin GUI served by the same Hono process, RFC 10017 (BCP 212, August 2026) says OAuth is often unnecessary. It recommends a server-side cookie session (Secure, HttpOnly, SameSite=Strict, `__Host-` prefix, no Domain) plus a real CSRF defense. If OAuth is used for the GUI, a backend-for-frontend (tokens never reach the browser) is "strongly recommended" for personal-data apps. A browser public client with PKCE is the least secure pattern. The strongest and simplest posture is to keep the GUI off the public hostname: bind it to 127.0.0.1 behind Tailscale Serve and trust Tailscale's identity headers. That only holds if the backend cannot be reached except through Serve.

### Cited Findings
- "OAuth 2.0 for Browser-Based Applications" is now **RFC 10017 / BCP 212, August 2026** (formerly draft-ietf-oauth-browser-based-apps, last draft -27). It describes three patterns, from most to least secure. (1) BFF, a confidential client where tokens never reach the browser, "strongly recommended" for business, sensitive and personal-data applications. (2) Token-Mediating Backend, where the access token still reaches the browser. (3) Browser-based public client with PKCE, which is "vulnerable to all the attack scenarios" described. — [IETF Datatracker: draft-ietf-oauth-browser-based-apps](https://datatracker.ietf.org/doc/draft-ietf-oauth-browser-based-apps/); [RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html)
- RFC 10017 §7.1 "Single-Domain Browser-Based Applications (Not Using OAuth)": "Too often, simple applications are made needlessly complex by using OAuth to replace the concept of session management." Same-domain frontend + API apps can use server-side cookie sessions instead. Reasons it lists for still using OAuth: centralized login/MFA, library support, future flexibility. — [RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html)
- RFC 10017 §6.1.3.2 cookie rules: MUST `Secure` and `HttpOnly`. SHOULD `SameSite=Strict`, `Path=/`, no `Domain`, and an HTTP-set prefix such as `__Host-Http-`. SameSite=Strict "falls short when the BFF is hosted alongside other applications within the same site". A CSRF defense is MUST, with CORS plus a custom request header recommended and anti-forgery or double-submit tokens as an alternative. — [RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html)
- RFC 10017 §8: localStorage and sessionStorage are readable by any malicious JS on the origin. In-memory tokens are lost on reload. — [RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html)
- OWASP CSRF Cheat Sheet: synchronizer token (stateful apps), signed double-submit cookie (stateless apps), Fetch Metadata (`Sec-Fetch-Site`, rejecting cross-site unsafe methods), custom request headers (relying on CORS preflight with an exact origin allowlist), and full-origin `Origin`/`Referer` checks that reject `null`. `__Host-` prefix. SameSite is defense in depth and "does not replace a proper CSRF defense in most deployments". Never change state on GET. Re-authentication for high-risk actions. No date shown. — [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- Hono's built-in `csrf()` middleware checks `Origin` and `Sec-Fetch-Site` ("allowed if either validation passes"; default same-origin). It applies only to unsafe methods **with form-sendable content types** (`application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`). — [Hono: CSRF middleware](https://hono.dev/docs/middleware/builtin/csrf)
- Tailscale Serve: `tailscale serve 3000` proxies tailnet traffic to `http://127.0.0.1:3000` and requires HTTPS certificates in the tailnet. It adds `Tailscale-User-Login`, `Tailscale-User-Name` and `Tailscale-User-Profile-Pic`, plus `Tailscale-App-Capabilities` with `--accept-app-caps` on v1.92+. These are added only for tailnet traffic, not Funnel or tagged devices, and Serve strips incoming copies. Tailscale advises having the backend "listen only on localhost", since otherwise "any user could supply their own header values". Page last validated **2026-01-20** (over 9 months old, possibly stale). — [Tailscale: Serve](https://tailscale.com/kb/1312/serve)
- MCP Streamable HTTP security warning: servers "MUST validate the `Origin` header ... to prevent DNS rebinding attacks", "SHOULD bind only to localhost (127.0.0.1)" when local, and "SHOULD implement proper authentication". Spec version 2025-11-25 (over 6 months old; a newer revision may exist). — [MCP spec 2025-11-25: Transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)
- mem today: REST and MCP both authenticate with per-bank bearer API keys from the `Authorization` header. OAuth for MCP is planned but deferred. — repo `src/attachment/rest/app.ts` (`bearerToken()`), `ARCHITECTURE.md` lines 7 and 114 (local files, read only)

### Inferences
- **Recommended default: same-origin cookie session issued by Hono, scoped to a GUI-only API prefix.** A `/login` page served by Hono (password or passkey) sets a `__Host-` session cookie with Secure, HttpOnly, SameSite=Strict and Path=/. The GUI calls a cookie-authenticated prefix such as `/admin/api/...` that maps to the same handlers. Keep `/v1/banks/:bankId/...` and `/mcp` bearer-only, and never accept the cookie there. Cookie auth then never widens the attack surface of the MCP and REST endpoints that AI clients use.
- **The CSRF check has to be custom for a JSON SPA.** Hono's `csrf()` skips `application/json` requests. For the cookie-authenticated prefix, add an explicit `Sec-Fetch-Site: same-origin` / exact-`Origin` check on every unsafe method regardless of content type (OWASP Fetch Metadata plus Origin verification), plus a required custom header (for example `X-Mem-CSRF: 1`), which RFC 10017 recommends for BFFs. Add re-authentication before erase and before export, per OWASP's guidance on high-risk actions.
- **OAuth for the GUI only pays off once mem's MCP OAuth authorization server exists.** If it is built, the GUI should be a BFF: Hono runs the authorization code + PKCE flow server-side as a confidential client and keeps tokens in the server-side session behind the same `__Host-` cookie. It should not be a browser public client holding tokens in memory or localStorage. For one user on the same origin, RFC 10017 §7.1 explicitly endorses skipping OAuth.
- **Local-only or tailnet-only mode is strongest for a one-user admin tool.** Bind the GUI listener to 127.0.0.1 and front it with `tailscale serve`. Trust `Tailscale-User-Login` only when the request arrives on that loopback listener, and match it against one configured login. This needs no passwords or login page. Caveats:
  - (a) If the MCP endpoint must stay public (remote MCP clients such as Claude or ChatGPT need a public HTTPS URL), the same Hono process would need two listeners: public for `/v1` and `/mcp`, loopback for the GUI. Alternatively, the GUI routes must reject any request that does not come from loopback or that lacks the header. Otherwise a public request could spoof the header, which is exactly Tailscale's warning.
  - (b) Loopback alone does not stop DNS rebinding. Keep an `Origin`/`Host` allowlist check on the GUI too, mirroring the MCP rule.
  - (c) `@hono/node-server`'s `serve()` currently uses Node's default host, so binding is a code change in `main.ts`.
- **Same public hostname as MCP vs a private one.** On the public hostname, the GUI's login page and admin API are internet-reachable: brute-force and credential stuffing hit the login, any XSS in the GUI runs on the same origin as `/mcp` and `/v1`, and erase/export become remotely triggerable with a stolen session. SameSite=Strict still protects against other sites, but RFC 10017 notes it "falls short" if other apps share the registrable domain. A private hostname (tailnet-only) removes the public login surface entirely. It also lets the GUI's origin differ from the MCP origin, so the session cookie is never even sent to the MCP host. For a personal tool holding personal data, the private hostname is the better default; the public hostname plus cookie session is the fallback.

### Gaps
- I did not check whether a newer MCP spec revision than 2025-11-25 changes the transport security wording, or whether the Tailscale Serve page changed after its 2026-01-20 validation.
- The OWASP pages show no last-updated date.
- Whether @hono/node-server 2.x can bind two listeners from one `serve()` call (versus two `serve()` calls sharing one app) was not checked.

## Q5. Testing the GUI

### Takeaway
Playwright end-to-end tests against the real `npm start` server fit every shape, because `webServer` can start the Hono process. Vitest Browser Mode has been stable since Vitest 4 (October 2025) and can run React component tests next to mem's existing Node tests through `projects`. mem would have to move from vitest 3.2 to 4 or 5 first.

### Cited Findings
- Playwright `webServer`: `command` (for example `npm run start`), `url` (ready on 2xx/3xx/400-403), `reuseExistingServer: !process.env.CI`, `timeout` (default 60000), `env` (adds `PLAYWRIGHT_TEST=1`). It can be an array to start several servers. Pair it with `use.baseURL`. — [Playwright: Web server](https://playwright.dev/docs/test-webserver)
- @playwright/test is at 1.64.1 (npm, published 2026-10-28). — [npm: @playwright/test](https://www.npmjs.com/package/@playwright/test)
- Vitest 4 (2025-10-22): "With this release we are removing the `experimental` tag from Browser Mode." Providers moved to separate packages (`@vitest/browser-playwright`, `@vitest/browser-webdriverio`, `@vitest/browser-preview`). Vitest 4 added `toMatchScreenshot` visual regression and `toBeInViewport`. — [Vitest 4 blog](https://vitest.dev/blog/vitest-4)
- The Vitest docs show v5.0.5. Setup is `npx vitest init browser`, then `test.browser.enabled`, `provider: playwright()` and `instances: [{ browser: 'chromium' }]`. There is an official `vitest-browser-react`. Use `projects` to run Node unit tests and browser tests side by side. Headless mode needs the playwright or webdriverio provider; `preview` is not for CI. — [Vitest: Browser Mode](https://vitest.dev/guide/browser/)
- vitest is at 5.0.5 (5.0.0 published 2026-09-03; 4.1.12 on the `V4` tag; 3.2.7 on the `V3` tag). mem pins `^3.2.4`. — [npm: vitest](https://www.npmjs.com/package/vitest); repo `package.json`

### Inferences
- **Shape 2 with Vite + React.** Use Playwright for 3-6 end-to-end flows: list facts, search with an as-of date, confirm/dispute/correct, export, erase, read the audit log. Run them against `npm run build:web && npm start` with a seeded test bank, using the same Postgres `mem_test` setup the existing suite uses. Add Vitest Browser Mode with `vitest-browser-react` only if component logic grows (for example the supersession-history view). Both live in one package: one `playwright.config.ts`, and a `projects` entry in the existing vitest config.
- **Hono JSX + htmx.** Most behavior can be tested with the existing Node vitest suite by requesting HTML from the Hono app and asserting on the markup, because rendering happens on the server. Playwright then covers only the htmx interactions. This is the cheapest test story.
- Upgrading vitest 3 → 5 is a prerequisite for browser mode and touches the whole existing test suite. Playwright-only E2E needs no vitest upgrade.

### Gaps
- Hono's testing helpers (`app.request()`, `testClient`) were not fetched this session. The Hono JSX testing inference above rests on general Hono knowledge, not a cited page.
- Breaking changes from Vitest 3 to 5 were not reviewed.
