# Honcho (plastic-labs/honcho), re-read for spike stage 2 on 2026-10-23

Sources: the repository at `main` (commit 522148b, 2026-10-23: `src/`, `.env.template`,
`docker-compose.yml.example`, `CHANGELOG.md`), the public OpenAPI (https://honcho.dev/docs/v3/openapi.json,
version 3.4.1), docs.honcho.dev, GHCR tags and npm. Then the containers (`npm run engines:honcho:up`).

## What changed since the research report

- **v3.4.1 is tagged and on GHCR (2026-10-23)** though the GitHub release object still says v3.4.0
  (2026-10-22). 3.4.1: certifi bump, uv 0.13.5, filter fix, LLM 4xx no longer retried,
  `SUMMARY_MAX_INPUT_TOKENS`. 3.4.0: `uid` on responses, named-scope API keys, a migration adding
  `deletion_generation` and queue indexes (needs `btree_gin`).
- License AGPL-3.0 unchanged. Image `ghcr.io/plastic-labs/honcho:v3.4.1` (not on Docker Hub),
  arm64 and amd64, about 120 MB compressed. One image, two processes: API (`fastapi run`, port
  8000) and the deriver (`python -m src.deriver`); without the deriver nothing is extracted.
- Needs its own Postgres with `vector`, `pg_trgm`, `btree_gin` (upstream `database/init.sql`,
  copied to `docker/honcho-init.sql`). Redis is optional upstream but see the cache finding below.
- **The deriver can call Anthropic directly** (`DERIVER_MODEL_CONFIG__TRANSPORT=anthropic`), which
  the report doubted; embeddings are OpenAI or Gemini only. Default model is still `gpt-5.4-mini`.
- Auth is off by default; with `AUTH_USE_AUTH=true` the admin token is minted inside the container
  (`src.security.create_admin_jwt`, HS256 over `AUTH_JWT_SECRET`); `npm run engines:honcho:admin-jwt`.
- Official TypeScript SDK `@honcho-ai/sdk` 2.7.0 (Apache-2.0, 2026-10-22, depends on zod 4).
  Every client is bound to one workspace and get-or-creates it lazily on the first call that needs it
  (`peer`, `session`, `sessions`, `search`); `workspaces()` and `deleteWorkspace()` do not.

## Facts that decided the adapter (`src/retrieval/infrastructure/honcho/honcho-engine.ts`)

| Need of the port | What Honcho offers | Mapping |
|---|---|---|
| Summaries | The deriver also summarises sessions (every 20 / 60 messages, `SUMMARY_*`), an LLM cost and a second copy of the text that `observe_me` does not cover. | The adapter's sessions are created with `summary.enabled = false`. |
| Index a fact we already extracted | Conclusions can be created directly (`POST .../conclusions`) but carry no metadata, so our id could not come back. Messages carry metadata, a client-set `created_at`, and are searchable (semantic over `message_embeddings` + ILIKE, RRF-fused, `limit` up to 100). | One workspace per bank, peer `subject`, sessions `facts` and `episodes`, all `observe_me: false` so the deriver does not re-extract. A fact or episode is a message with metadata `refId`, `kind`, `validFrom`, `validTo`, `retracted`. |
| Write returns when recallable | New messages are embedded by a background task ("searchable within seconds"); a search right after the write can miss it (seen in the contract run). | Index waits, bounded (15 s), until a search filtered by `metadata.refId` finds the message. |
| Retract | No message delete. `PUT .../messages/{id}` updates metadata. | Flip `retracted`; recall filters. The port gives no bank id: every workspace with our prefix is scanned. |
| Point-in-time | None on search, representation or chat (chat filters accept only `session_id`). `created_at` and metadata equality filters exist on search/list/query. | `metadata.retracted = "false"` and `created_at <= asOf` (our validFrom) are pushed into the search; `validTo` and kind are filtered here over an over-fetch (5x limit, at least 20, at most 100). |
| Scores | Search returns an ordering, no score. | `1/rank`. |
| Count | `messages/list` returns `total`; `workspaces` list with `filters: {id}` shows existence without creating. | Sum over the workspace's sessions; missing workspace = 0. |
| Purge with proof of zero | `DELETE session` and `DELETE workspace` return 202 and enqueue a deriver job (`task_type: deletion`); workspace delete is refused (409) while sessions are active. The API keeps serving the data until the job runs. | Delete sessions, delete workspace, poll until the API reports nothing for two consecutive readings (idle deriver poll shortened to 2 s in our compose). **Checked in Honcho's Postgres right after a purge returned:** `messages`, `message_embeddings`, `sessions`, `workspaces` and `queue` all zero for that workspace, so "not listed" means deleted, and a stopped deriver shows as a purge timeout. |
| Embedder id filter | Honcho owns its embedder; `EMBEDDING_VECTOR_DIMENSIONS` is immutable per deployment. | Not expressible. |

## Findings from running it

- **Provider swap to Claude 5 fails (upstream defect, 3.4.1).** With `DERIVER_MODEL_CONFIG__TRANSPORT=anthropic`
  and `MODEL=claude-opus-5-5` every deriver call gets HTTP 400 `This model does not support assistant
  message prefill`: Honcho's Anthropic backend prefills an assistant `{` for JSON output and its
  `_supports_assistant_prefill` check exempts only names starting `claude-opus-4`, `claude-sonnet-4`,
  `claude-haiku-4` (the generations are the wrong way round: the 4.5 models accept prefill, the 5
  models reject it; verified with one-shot requests to the API). A `thinking_budget_tokens` turns the
  prefill off but then Honcho sends `thinking.type=enabled`, which Claude 5 also rejects (`Use
  "thinking.type.adaptive"`), and the `provider_params.extra_body` passthrough does not replace that
  typed SDK argument. No configuration drives a Claude 5 model; `claude-sonnet-4-5` works unchanged.
  **The deriver reports the failed work units as completed** (`queue/status` shows 12/12 done, the
  `queue` table has `error` set, zero conclusions); arm D therefore records the conclusion count
  after each ingestion. Consequence for the spike: arm D extracts with Sonnet 4.5 while arms B and
  C extract with Opus 5.5; the answering model is the same in all arms.

- **Stale cache after deletion (upstream defect, 3.4.1).** With `CACHE_ENABLED=false` Honcho still
  caches workspaces, peers and sessions in-process (cashews `mem://`, default TTL 300 s). The
  deriver deletes the rows in its own process, so the API's get-or-create keeps returning the deleted
  workspace (same `uid`, zero rows in Postgres, verified) and the next peer insert fails its foreign
  key, surfaced as `409 Unable to create or get peers`. A deleted workspace name is unusable for up
  to five minutes. Upstream's compose runs Redis; with `CACHE_ENABLED=true` and a shared Redis the
  invalidation reaches the API and the contract passes. Our compose therefore runs Redis.
- The idle deriver backs its poll off to 30 s by default (`DERIVER_POLLING_SLEEP_MAX_INTERVAL_SECONDS`),
  which also delays deletions and tests; set to 2 s in our compose. `DERIVER_FLUSH_ENABLED=true` so
  small sessions do not wait for a 512-token batch or 30 minutes.
- No token usage anywhere in API responses. The deriver publishes Prometheus counters
  (`deriver_tokens_processed_total{task_type,token_type,component}` on its port 9090, mapped to
  127.0.0.1:9091); they are process-wide, so arm D ingests one conversation at a time and records
  counter deltas. The dialectic path's own usage is only in logs / Prometheus of the API process.
- Auth on (`AUTH_USE_AUTH=true`) works with the SDK's `apiKey` as a Bearer JWT; unauthenticated
  calls get 401 while `/health` stays open.
